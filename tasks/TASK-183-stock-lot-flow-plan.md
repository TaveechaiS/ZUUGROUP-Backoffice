2. บันทึกเพิ่มสินค้าไม่เพิ่มstock รับเข้ามีคลังdefaultMAINและเลือกเปลี่ยนได้ เก็บล็อตแยกคงเหลือในแต่ละคลัง โอนจากMAINไปMARKETINGตามจำนวนคงเหลือจริง รวมทุกคลังคงเดิม.
3. บันทึกใกล้หมด/หมดเฉพาะยอดMAINตาม0/1–50ที่ยืนยันแล้ว ไม่รวมMARKETING/DISPOSAL. ยังไม่เปลี่ยนสูตรจอง/พร้อมขาย.
4. รับคำตอบเวลาจากวันรับเข้าหรือก่อนหมดอายุ และmanualยืนยันหรืออัตโนมัติ; จากนั้นสรุปจำนวนเดือน/วันและย้ายเต็มหรือบางส่วนก่อนแผนimplementation.

## งานเปิด

นิยามเวลา, เกณฑ์เวลา, วิธีmanual/auto, ย้ายเต็ม/บางส่วน และสินค้าที่ไม่หมดอายุ. กฎเดิมยืนยันย้ายหลังของย้ายจริงไม่ถูกแทนจนได้รับคำตอบใหม่.

## แผนหน้ารายงานและเติมของฉบับเสนอ

เจ้าของขอPlanก่อน และถามว่าต้องเห็นจำนวนล็อต/เวลารายล็อต/รวมทุกคลังกับทางลัดเติมของ. ข้อด้านล่างเป็นแผนเสนอให้ตรวจ ยังไม่เริ่มcode/DB.

### 1. สรุปสินค้าในตารางหลัก

รหัส, ชื่อ, หน่วย, คลังหลัก, คลังการตลาด, คลังรอทำลาย, รวมทั้งหมด, จำนวนล็อต, สถานะ. ยอดMAINเป็นฐานใกล้หมด/หมดแม้รวมทุกคลังยังมีของ. จำนวนล็อตเสนอdistinctล็อตที่ยังมียอดคงเหลือ>0ในscopeนั้น; lotเดียวสองคลังจำนวนรวมยัง1ล็อต. ประวัติล็อตหมดแล้วไม่ลบ เก็บในประวัติ. จำนวนล็อตแต่ละคลังแสดงในdetailได้.

### 2. คลิกดูล็อตและเวลา

กดจำนวนล็อตเปิดรายละเอียดล็อตของสินค้าแยกMAIN/MARKETING/DISPOSAL; กดยอดคลังเปิดรายการเฉพาะคลังที่กด. แต่ละล็อตแสดงคลัง เลขล็อต วันรับเข้า วันผลิต วันหมดอายุ อายุ/วันเหลือและคงเหลือ ต้นทุนเฉพาะสิทธิ์เดิม. MAINสถานะตามจำนวนสินค้า; MARKETINGวันเหลือรายล็อต; DISPOSALไม่มีป้ายสถานะ แต่คงข้อมูลล็อต/วันที่ให้ตรวจย้อนหลัง. ไม่แสดงวันหมดอายุเดียวแทนทั้งสินค้าหลายล็อต.

### 3. เติมของจากสถานะ

กดหมด/ใกล้หมดMAINไปเพิ่มสต็อก ไม่ใช่เพิ่มสินค้า. PrefillproductID/ชื่อ/รหัส/หน่วย และdefaultMAIN. ผู้ใช้กรอกล็อต/จำนวน/ต้นทุน/วันผลิต/หมดอายุจริงและเปลี่ยนคลังได้. ไม่prefillต้นทุน/ล็อต/วันที่เก่าหรือปริมาณรับที่ระบบยังไม่รู้. การคลิกไม่เพิ่มยอด จังหวะยืนยันรับเป็นตามSpecsรับเข้าเดิมที่ต้องตรวจcontractก่อนimplementation.

### 4. ไหลล็อตตามเกณฑ์

MAIN→MARKETING→DISPOSAL เป็นการโอนlotเดิมและจำนวนคงเหลือจริง ต้นทางลดปลายทางเพิ่มเท่ากัน พร้อมhistory. ถ้าย้ายเต็มล็อต1จำนวน20จากMAINที่มีล็อต2จำนวน50: MAIN50/1ล็อต MARKETING20/1ล็อต รวม70/2ล็อต. ถ้าจ่ายไปบางส่วนก่อนโอน ใช้ยอดปัจจุบัน ไม่ใช้ยอดรับแรก. ไม่กำหนดวันที่หรือย้ายอัตโนมัติในรอบแผน.

### 5. ลำดับ implementation หลังแผนพร้อม

1. ยืนยันตาราง/วิธีนับล็อต/ทางลัด และOPENเวลา/เกณฑ์สองการโอน/manual-auto/วันหมดอายุกรณีพิเศษ.
2. บันทึกcontractAPIและเส้นทางreport/detail/รับ/โอน พร้อมACTIVEและแผนย่อยตามไฟล์จริงก่อนแก้.
3. ปรับAPIสรุปยอด/ล็อตและscopeสถานะMAIN แล้วรายงาน/รายละเอียดอ่านข้อมูล.
4. ทำฟอร์มรับเลือกproduct/defaultMAIN พร้อมวันผลิต/หมดอายุ/ต้นทุน/attachmentsที่ต้องสรุป.
5. เชื่อมทางลัดเติมของ แล้วงานย้ายล็อต/historyตามวิธีที่เจ้าของยืนยัน.

ไฟล์คาดหมาย: src/app/products/page.tsx, stock/page.tsx, stock/[warehouse]/page.tsx/layout.tsx; routeรับเข้า/ดูล็อตต้องเลือกหลังแผนยืนยัน; src/server/operations/service.ts/handlers.ts, src/types/api/operations.ts, componentStatusBadgeกลางและscriptintegrationตามขอบเขตจริง. Prisma/migrationเฉพาะเมื่อข้อมูลที่ยืนยันต้องเพิ่ม ไม่สร้างตารางล่วงหน้า.

### ตรวจรับเมื่อทำจริง

รับ20+50MAINต้อง70/2ล็อต; ย้ายล็อต20ต้องMAIN50/MARKETING20/รวม70/2ล็อต; MAINขึ้นใกล้หมดและกดเปิดฟอร์มสินค้าถูกตัวแต่ยังไม่เพิ่มยอด. MARKETINGแยกวันเหลือรายล็อต ไม่มีใกล้หมด; DISPOSALไม่มีสถานะ. คำสั่งย้ายซ้ำไม่หักซ้ำ รวมยอดก่อน/หลังเท่าเดิม ยอดติดลบไม่ได้. ทดสอบcode/APIตามTaskใหม่เมื่อเปิดimplementation.

## เพิ่มข้อยืนยันอายุและสถานะตามคลัง

เจ้าของให้มีข้อมูลอายุยา วันผลิตและวันหมดอายุรายล็อต. ข้อเสนอคำนวณอายุแทนการกรอกเองยังไม่ถือเป็นคำยืนยันใหม่.

| คลัง | การแสดงสถานะ |
|---|---|
| MAIN | จำนวน0หมด, 1–50ใกล้หมด ตามยอดMAIN |
| MARKETING | เวลาที่เหลือก่อนหมดอายุของแต่ละล็อต เช่นเหลือ30วัน ไม่ใช้ใกล้หมด |
| DISPOSAL | ไม่แสดงสถานะ |

กรณีสินค้า2ล็อตวันหมดอายุต่างกันต้องแสดงวันเหลือแยกตามล็อต; ถ้ารายงานสรุปสินค้าแถวเดียวต้องสรุปวิธีแสดงก่อนcode ไม่เดาเลือกล็อตหนึ่งให้ทั้งสินค้า. กรณีหมดอายุวันนี้/เลยวัน/ไม่ทราบวันและเกณฑ์สีOPEN. เมื่อทำUIใช้StatusBadgeกลาง/Bangkokdayตามมาตรฐาน. รอบนี้ขอบเขตยังเอกสารสี่ไฟล์เดิม ไม่API/DBหรือเคลื่อนยอด.
