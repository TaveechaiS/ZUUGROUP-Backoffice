# Specs รายโมดูล — Auth, RBAC และจัดการผู้ใช้

**รหัส:** SPEC-MODULE-AUTH-USER-001
**สถานะ:** เจ้าของโครงการให้เดินหน้าตามเอกสารหลังสรุป OPEN-17 ขั้นต่ำ 8 ตัวอักษร
**อ้างอิง:** Project Specs §7, §8.1, §18.3, §27; OPEN-17; G-04; TASK-037

## 1. ขอบเขต

เพิ่มการเข้าสู่ระบบจริงด้วย Supabase Auth, การตรวจ Role ที่ Server และการจัดการบัญชีผู้ใช้จาก `/users`. ใช้กับสี่ Role ที่อนุมัติแล้ว: Admin, Sales, Manager, Accounting & CFO; ไม่มี Role Inventory.

Task นี้วางฐาน Auth/RBAC และให้ Admin จัดการบัญชี ไม่เปิดการทำงานของโมดูลธุรกิจที่ยังไม่มี permission matrix หรือ Specs รายโมดูล.

หน้า `/users` แสดงรายชื่อและลิงก์ไปหน้าจัดการ; `/users/create` เป็นหน้าเพิ่มบัญชี; `/users/<รหัสพนักงาน>` เป็นหน้ารายละเอียด/แก้บัญชี เช่น `/users/admin`. ฟอร์มเพิ่ม แก้ ตั้งรหัส และคำสั่งเปลี่ยน Role/สถานะอยู่บนหน้าแยก ไม่เปิด modal บนรายชื่อ. รหัส `create`, `.` และ `..` เป็นคำสงวน; รหัสยาวไม่เกิน 40 ตัวอักษรและไม่มีเครื่องหมายคั่น URL หรืออักขระควบคุม. เมื่อแก้รหัสพนักงานต้องนำทางไป URL ใหม่.

## 2. ข้อกำหนดที่ยืนยันแล้ว

- ใช้อีเมลและรหัสผ่านผ่าน Supabase Auth; ไม่มี public sign-up.
- Admin สร้างบัญชี กำหนดหนึ่ง Role ต่อผู้ใช้ ระงับ/เปิดใช้งาน กู้คืน และตั้งรหัสผ่านใหม่ให้; ไม่ส่ง invitation/reset email หรือลิงก์.
- Supabase Auth เก็บ credentials; ตารางธุรกิจเก็บข้อมูลพนักงาน, Role, สถานะ และรหัสเชื่อม Auth โดยไม่เก็บ password/hash.
- ผู้ไม่มี session ถูก redirect ไป Login; ผู้มี session แต่บัญชีถูกระงับ/ลบหรือไม่มี Role ที่ยอมรับ ต้องถูกปฏิเสธที่ Server.
- หากการอ่านบัญชีหลังยืนยันตัวตนพบ Prisma `P1017` เพราะ connection ปิด ให้ลองอ่านใหม่ได้หนึ่งครั้งเฉพาะคำสั่งอ่าน; หากยังล้มเหลว ให้จบ Session ที่เพิ่งสร้างและแจ้งว่าระบบเชื่อมต่อข้อมูลชั่วคราวไม่ได้ โดยไม่แสดง stack trace หรือบอกรหัสผ่านผิด.
- การตรวจสิทธิ์ต้องอยู่ใน Server Page/Route Handler/Server Action ทุกเส้นทาง; Proxy ใช้ช่วย refresh/redirect ได้แต่ไม่แทน authorization.
- Role และสถานะมาจากฐานข้อมูลธุรกิจ ไม่รับจาก Browser และไม่ใช้ `user_metadata` ตัดสินสิทธิ์.
- การเปลี่ยนสถานะ/Role มีผลกับ request ถัดไป แม้ผู้ใช้ถือ session เดิม; token/cookie อย่างเดียวไม่ยืนยันว่า account ยัง active.
- ถ้าการกระทำจะทำให้ไม่มี Admin ที่เข้าใช้ได้เหลือ ให้ปฏิเสธโดยตรวจซ้ำแบบ atomic เพื่อกัน race condition.
- Admin ห้ามระงับ ลบเชิงตรรกะ หรือเปลี่ยน Role ออกจาก Admin ของบัญชีที่ตนกำลังใช้งาน แม้ยังมี Admin คนอื่น; ให้ Admin อีกบัญชีเป็นผู้ดำเนินการ เพื่อไม่ให้ผู้ทำคำสั่งตัดสิทธิ์ Session ของตนเองกลางการนำทาง.
- Admin ตั้งรหัสเริ่มต้น/รหัสใหม่ผ่าน Server เท่านั้น; รหัสผ่านไม่ปรากฏในตาราง รายละเอียด Audit log หรือ log application.
- หาก Auth user ถูกสร้างแล้วบันทึกธุรกิจล้มเหลว การ retry ต้องไม่สร้างบัญชีซ้ำ และต้องมีทางชดเชย/กู้คืนที่ตรวจสอบได้.
- Admin ที่กู้คืนจากภายนอกเว็บใช้ [คู่มือ Recovery](../../runbooks/admin-account-recovery.md); recovery utility ต้องอยู่ฝั่งเซิร์ฟเวอร์และทดสอบก่อน Auth เปิดใช้จริง.
- เมื่อเจ้าของโครงการกู้คืน Admin ที่เคยถูกลบเชิงตรรกะ เครื่องมือต้องล้าง `deleted_at`, `deleted_by`, `delete_reason` พร้อมคืนสถานะ Active และ Role Admin; Audit ต้องแสดงสถานะก่อน/หลังโดยไม่เก็บรหัสผ่าน.

## 3. Role และสิทธิ์ในขอบเขตนี้

| Role | หน้าจัดการผู้ใช้ | การเข้าถึงที่ระบุ |
|---|---|---|
| Admin | สร้าง/ดู/แก้/ระงับ/เปิดใช้งาน/เปลี่ยน Role/ตั้งรหัส/ส่งออกตามข้อกำหนด | จัดการระบบตามขอบเขตที่ยืนยัน; ปฏิเสธการเอาสิทธิ์ Admin คนสุดท้าย |
| Sales | ไม่มี | ปฏิเสธ `/users` และทุกคำสั่งจัดการบัญชี |
| Manager | ไม่มี | ปฏิเสธ `/users` และทุกคำสั่งจัดการบัญชี |
| Accounting & CFO | ไม่มี | ปฏิเสธ `/users` และทุกคำสั่งจัดการบัญชี |

Permission ของโมดูลธุรกิจที่ยัง OPEN ให้ปฏิเสธจนมี Specs ที่อนุมัติ ห้ามใช้ Role เพียงอย่างเดียวเพื่อสรุป Data scope.

เจ้าของโครงการยืนยัน 2026-09-30 ว่ายังไม่มีข้อมูลจริงสำหรับกำหนดรายละเอียดสิทธิ์รายโมดูล/รายข้อมูล; หน้าตัวอย่างอาจแสดงต่างกันตาม Role เพื่อดูแนวทาง UI แต่ยังไม่ใช่ข้อยืนยันสิทธิ์ใช้งานจริง. การจำกัดสิทธิ์ละเอียดต้องรอข้อมูลและกติกาที่เจ้าของโครงการให้ภายหลัง. ขอบเขต Auth รอบนี้ยังคงตรวจฝั่ง Server ว่าเฉพาะ Admin จัดการ `/users` และ API ผู้ใช้ได้ และผู้ถูกระงับ/ลบเข้าใช้ไม่ได้.

## 4. วงจรบัญชี

1. Admin กรอกชื่อ อีเมล Role และรหัสผ่านที่ตั้งให้ผู้ใช้; Server สร้างรหัสพนักงานที่ไม่ซ้ำให้อัตโนมัติ โดยไม่ให้ Admin กรอกในขั้นตอนเพิ่มบัญชี. Admin เปลี่ยนรหัสพนักงานได้ในหน้าแก้ข้อมูลภายหลัง.
2. Server ตรวจรูปแบบ/ค่าซ้ำและสร้าง Supabase Auth user โดยไม่ส่ง email; การยืนยันอีเมลให้ดำเนินผ่าน trusted admin flow เพื่อรองรับ email/password โดยไม่มี verification mail.
3. Server สร้าง/เชื่อมแถว user business กับ `auth_accounts`; ถ้าขั้นตอนหนึ่งล้มเหลวต้องแสดงสถานะกู้คืนได้และ retry แบบ idempotent.
4. การระงับ/ลบเชิงตรรกะปิดการเข้าถึงทันทีจากการตรวจ account state ฝั่ง Server; การ Restore ต้องทำโดย Admin.
5. การเปลี่ยน Role หรือรหัสผ่านบันทึก Audit event; ห้ามเก็บ password, token หรือ Secret ใน event.
6. ไม่มี self-service password reset, email link หรือ invitation email.

### การลบและกู้คืนผู้ใช้ (เจ้าของโครงการยืนยันเพิ่มเติม)

- ปุ่มลบของ Admin เป็นการลบเชิงตรรกะเท่านั้น: เก็บแถวผู้ใช้, รหัสพนักงาน, อีเมล, Role, ความเชื่อมโยง Auth และประวัติไว้; บันทึกเวลา ผู้ลบ และเหตุผล. ไม่ลบบัญชี Supabase Auth.
- ผู้ใช้ที่ลบถูกปฏิเสธตั้งแต่คำขอถัดไปแม้มี Session เดิม; รายชื่อปกติซ่อนผู้ใช้ที่ลบ และมีมุมมอง “ลบแล้ว” ให้ Admin ค้นหา ดูผู้ลบ/เวลา/เหตุผล และกู้คืน.
- “รายการปกติ / ลบแล้ว” ในหน้า `/users` ต้องเป็นแท็บรูปแบบเดียวกับหน้าโมดูล ไม่ใช่ปุ่มเลือกมุมมองแบบทึบ; การเปลี่ยนแท็บยังอยู่ URL เดิมและรีเซ็ตหน้าตาราง.
- การกู้คืนต้องระบุเหตุผล, ตรวจอีเมล/รหัสพนักงานซ้ำและสถานะ Role ก่อนเปิดให้ใช้ตามสถานะเดิม; บันทึก Audit ทั้งการลบและกู้คืน. ผู้ใช้ที่ลบแล้วห้ามแก้ Role/ข้อมูล/รหัสหรือเปลี่ยนสถานะจนกว่าจะกู้คืน.
- คำสั่งลบต้องปฏิเสธหากทำให้ไม่มี Admin ที่ยังเข้าใช้ได้เหลืออยู่; ใช้การล็อกธุรกรรมเดียวกับการระงับ/ลด Role. การลบถาวรอยู่นอกขอบเขตนี้.

## 5. ข้อมูลและ authorization

- ยึด `users.id` เป็น business user id และ `auth_accounts(provider, provider_user_id)` เชื่อมกับ Supabase Auth ตาม Project Specs §18.3.
- บังคับ unique สำหรับอีเมล/employee code ที่กำหนดว่าไม่ซ้ำ และหนึ่ง `users` ต่อหนึ่ง Role.
- เจ้าของโครงการยืนยัน 2026-09-30 ว่ารายละเอียดข้อมูลผู้ใช้เพิ่มเติมจะกำหนดและเพิ่มภายหลัง; รอบนี้คงช่องข้อมูลที่ใช้งานอยู่ ไม่กำหนดฟิลด์ใหม่แทนเจ้าของโครงการ.
- เก็บ Role/สถานะใน business DB; `user_metadata` เป็นข้อมูลแก้ไขได้และไม่ใช้เป็น authorization.
- Server ต้องโหลด active user/Role ปัจจุบันก่อนใช้ protected actions; ห้ามเชื่อ role ที่ส่งใน request/body/query.
- Auth Admin Secret key ใช้เฉพาะ server module ที่ import `server-only`; ห้ามส่งเข้า Client Component, public env, error message หรือ log.
- Proxy ใช้เพื่อ refresh session/redirect แบบเร็วตาม Next.js 16; ทุกข้อมูล/API ยังต้องตรวจ session และ permission ซ้ำที่ Server.
- สิทธิ์ของโมดูลนอกขอบเขตนี้ deny-by-default จนมี Specs/Permission matrix อนุมัติ.

## 6. Audit และงานนอกขอบเขต

บันทึก event สำหรับการสร้างบัญชี เปลี่ยน Role ระงับ/เปิดใช้งาน ตั้งรหัส และ recovery โดยเก็บ actor, target, timestamp, action, request id และค่าก่อน/หลังเฉพาะฟิลด์ที่ไม่ลับ. ไม่เก็บ password, hash, session token, API key หรือ request body ทั้งก้อน. Task นี้ไม่ทำ Audit Logs UI, export, archive, purge หรือ retention automation; รายละเอียดเหล่านั้นยังติด G-10.

ไม่รวม permission ของโปรโมชัน/การอนุมัติ/ต้นทุน Manager (OPEN-01), Workflow ลูกค้าและคำสั่งซื้อ (OPEN-02), Storage (OPEN-10), migration ข้อมูลเดิม (OPEN-13), Sidebar positions (OPEN-16).

## 7. นโยบายที่เจ้าของโครงการกำหนด — OPEN-17

เจ้าของโครงการกำหนดขั้นต่ำรหัสผ่านเป็น **8 ตัวอักษร** รองรับ passphrase และไม่บังคับรูปแบบตัวพิมพ์/ตัวเลข/สัญลักษณ์ตายตัว; ให้ Supabase Auth บังคับนโยบายเดียวกันทั้งการสร้างและตั้งรหัสใหม่. นโยบาย OPEN-17 ได้ข้อสรุปและเจ้าของโครงการให้เดินหน้า implementation แล้ว.

## 8. Scenario ตรวจรับ

- Login สำเร็จ/ผิด, logout, session หมดอายุ, และเข้า protected URL โดยไม่ login.
- ทดสอบสี่ Role; เฉพาะ Admin เข้า `/users`; ปลอม Role ใน request หรือ `user_metadata` แล้วไม่ได้สิทธิ์เพิ่ม.
- เพิ่มผู้ใช้/Role เดียว/ตั้งรหัสโดยไม่กรอกรหัสพนักงาน: ระบบสร้างรหัสที่ไม่ซ้ำให้, เข้าใช้ได้, ไม่มี email; อีเมลซ้ำหรือรหัสพนักงานที่ Admin เปลี่ยนเป็นค่าซ้ำถูกปฏิเสธ.
- เข้าหน้า `/users/create` และ `/users/admin` ได้โดยตรงเมื่อเป็น Admin; Role อื่นถูกปฏิเสธ. หลังสร้างบัญชีไปหน้ารายละเอียดรหัสใหม่; หลังแก้รหัสพนักงาน URL เปลี่ยนตาม; รหัส `create` ถูกปฏิเสธ.
- Admin เปลี่ยนรหัส; ผู้ใช้เข้าได้ด้วยรหัสใหม่; ไม่มีรหัสลับใน response, DOM, logs หรือ Audit.
- ระงับ account ขณะ session เดิมยังอยู่; request ถัดไปถูกปฏิเสธ.
- ลบผู้ใช้ทดสอบแล้วไม่อยู่ในรายชื่อปกติ, Session เดิมใช้ไม่ได้, เห็นรายการใน “ลบแล้ว” พร้อมผู้ลบ/เวลา/เหตุผล; กู้คืนพร้อมเหตุผลแล้วกลับสู่รายชื่อปกติและสถานะเดิม โดย Audit มีทั้งสองเหตุการณ์.
- ลบ/ระงับ/ลด Role ของ Admin คนสุดท้ายถูกปฏิเสธ; concurrency test ยืนยันว่า Admin สองคนไม่สามารถลดกันพร้อมกันจนเหลือศูนย์.
- Admin ลองระงับ ลบ หรือเปลี่ยน Role ของบัญชีตนเองแล้วถูกปฏิเสธด้วยข้อความชัดเจน; บัญชีที่ลบแล้วลอง Login ต้องได้ข้อความบัญชีไม่พร้อมใช้งานและไม่เข้าสู่เว็บ.
- จำลองความล้มเหลวระหว่างสร้าง Auth/business records แล้ว retry; ไม่มีบัญชีซ้ำและมีทางตรวจ/กู้คืน.
- ใช้ owner-only recovery utility เมื่อไม่มี Admin ใน app; login และ Admin role กลับมาได้.

## 9. ⚠️ ต้องทดสอบโดยคุณ

หลัง implementation เปิด `/login` และ `/users` ด้วยบัญชีทดสอบของแต่ละ Role; ตรวจการเข้า/ออกระบบ, การเพิ่มผู้ใช้, การเปลี่ยน Role/รหัส, การระงับ session เดิม และกรณี Admin คนสุดท้ายตาม Scenario §8. ผลที่คาดคือ Server ปฏิเสธทุกสิทธิ์ที่ไม่ได้อนุมัติ, ไม่มีอีเมล/ลิงก์ และ recovery คืนการเข้าถึง Admin ได้.

## 10. บัญชี Admin คนแรก

เจ้าของโครงการขอใช้รหัสพนักงาน `admin` และอีเมล `admin@zuugroup.com` สำหรับบัญชีแรก; ชื่อแสดงใช้ `Admin` ระบบปัจจุบันล็อกอินด้วยอีเมล รหัสผ่านต้องเป็นค่าใหม่ที่เจ้าของโครงการป้อนบนเครื่องผู้ดูแลและยาวอย่างน้อย 8 ตัวอักษรตาม OPEN-17; ห้ามบันทึกรหัสผ่านในเอกสารหรือแชต
