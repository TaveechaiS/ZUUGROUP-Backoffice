## 1. เป้าหมายและขอบเขต

### 1.1 เป้าหมาย

ZUUGROUP เป็นเว็บหลังบ้านสำหรับธุรกิจจัดจำหน่ายยาและเวชภัณฑ์ B2B ใช้จัดการลูกค้า สินค้า คลัง จัดซื้อ การขาย การส่งของ การเงิน และรายงาน โดยเตรียมแทนเว็บเดิมและรับข้อมูลจริงภายหลัง

ผู้ใช้ต้องทำงานจากหน้าที่เกี่ยวข้องได้ด้วยขั้นตอนสั้น ข้อมูลระหว่างโมดูลเชื่อมกัน และทุกการเปลี่ยนข้อมูลตรวจสอบย้อนหลังได้ คนหรือ AI ตัวใหม่ต้องรับงานต่อจากเอกสารใน Git ได้

### 1.2 ขอบเขตรุ่นแรก

- เว็บภาษาไทยตามแบบและทรัพยากร Design ของผู้ใช้
- เข้าสู่ระบบด้วยอีเมลและรหัสผ่าน และแสดงข้อมูลตาม 4 Roles
- ฐานข้อมูลจริงบน Supabase พร้อมข้อมูลจำลองที่สร้างซ้ำได้
- เพิ่ม แก้ไข ดู ค้นหา กรอง และส่งออกข้อมูลตามสิทธิ์
- ระบบอนุมัติส่วนลดพิเศษและโปรโมชัน พร้อมประวัติการพิจารณา
- คลังสามประเภท การรับเข้า โอน จ่าย และบันทึกความเคลื่อนไหว
- การขาย จัดส่ง วางบิล รับชำระบางส่วน และแสดงลูกหนี้คงค้าง
- Soft Delete สำหรับข้อมูลหลัก การกู้คืนโดย Admin และการยกเลิกธุรกรรม
- Audit Log ของตารางที่ระบบดูแลทั้งหมด
- PDF 5 ประเภทตามข้อ 17
- Docker และคู่มือเริ่มงานหลัง Clone
- รายการทดสอบให้ผู้ใช้ตรวจเอง พร้อมแยกสถานะทำเสร็จออกจากผ่านตรวจรับ

### 1.3 ขอบเขตที่ยังไม่รวมในรุ่นแรก

- การนำข้อมูลจริงจากเว็บเก่าเข้า จนกว่าจะทราบรูปแบบข้อมูลและ Mapping
- การเผยแพร่เว็บ Production การซื้อบริการ และการย้ายระบบจริง
- ระบบแปลงหน่วยสินค้า จำนวนสินค้าแบบทศนิยม และการเปลี่ยนรูปแบบหน่วยระหว่างทำรายการ
- ใบกำกับภาษี ใบลดหนี้ และใบเพิ่มหนี้ จนกว่าจะได้ข้อกำหนดและแบบเอกสาร
- ระบบหลายภาษาในหน้าจอ รุ่นแรกมีเฉพาะภาษาไทย
- การสร้าง Design, Logo, Icon หรือชุดสีใหม่แทนสิ่งที่ผู้ใช้เตรียมไว้
- ระบบแผนที่ การอนุมัติลูกค้าใหม่ทุกกรณี และการอนุมัติทุกคำสั่งซื้อ ยังไม่ถือเป็นขอบเขตยืนยัน ดูข้อ 28

## 3. แหล่งข้อมูลและลำดับความสำคัญ

### 3.1 ลำดับเมื่อข้อมูลขัดกัน

1. คำสั่งหรือคำตัดสินล่าสุดของผู้ใช้ที่มีขอบเขตชัดเจน
2. Project Specs และ Specs รายโมดูลรุ่นที่ผู้ใช้อนุมัติ
3. Code Style ที่ส่งมา พร้อมข้อปรับสำหรับโครงการนี้ในข้อ 23
4. Plan และ Task ที่อ้างอิง Specs รุ่นที่อนุมัติ
5. เอกสารเก่า ตารางเมนู บทถอดเสียง และร่างก่อนหน้า ใช้ประกอบการตรวจสอบ

ข้อเสนอในคำตอบเก่าที่ผู้ใช้ยังไม่ยืนยันไม่กลายเป็นกฎอัตโนมัติ รุ่นเอกสาร `REVIEW` ไม่แทนรุ่น `APPROVED` จนกว่าจะได้รับการอนุมัติ

### 3.2 หลักฐานที่ใช้ในฉบับนี้

| แหล่งข้อมูล | การใช้และข้อจำกัด |

| ภาพ “ตัวอย่าง 1.png” และภาพหน้าเพิ่ม/แก้/ดู | ใช้กำหนดรูปแบบหน้าและลำดับองค์ประกอบ |

พบสมุดงานออกแบบเดิมซึ่งใช้ชุดเทคโนโลยีต่างจากที่ยืนยันใหม่ จึงไม่ถือว่าเป็นโครงแอปหลังบ้านที่อนุมัติแล้ว ตำแหน่ง Repository ของแอปใหม่ยังต้องกำหนดก่อนพัฒนา

## 4. ภาษาและรูปแบบข้อมูล

### 4.1 คำบนหน้าจอ

- ใช้คำสั้นและคุ้นเคย เช่น “ลูกค้า”, “สินค้า”, “ผู้ใช้งาน”, “ตั้งค่าระบบ”

## 6. หน้าจอและการออกแบบ

### 6.1 ต้นแบบและทรัพยากร

- ใช้แบบที่ผู้ใช้ทำไว้ใน Figma เป็นหลัก: คัดลอกโครงเดิมและเปลี่ยนเนื้อหาตามหน้าที่
- Sidebar หลักใช้สีน้ำเงิน `#1A58A7`; สีอื่น ระยะ ขนาด Font, Icon, Logo และสถานะยึดทรัพยากรที่ได้รับ
- ใช้ HeroUI ในการพัฒนา แต่ปรับให้ตรงแบบของผู้ใช้
- ผู้ใช้เป็นผู้ออกแบบ Figma; AI ทำ Specs/Plan/โค้ดตามงานที่ได้รับ ไม่แก้ Figma โดยพลการ
- หากขาด Component หรือ Asset ให้ระบุสิ่งที่ขาดและส่วนที่ได้รับผลกระทบ แล้วถามผู้ใช้ก่อนเลือกของใหม่

### 6.2 หน้ารายการ

ลำดับองค์ประกอบ: Side Main → Topbar → Side Secondary เมื่อจำเป็น → Tab bar → Filter → ตารางหรือข้อมูล → Pagination/Export ตามแบบ

- Tab แยกสถานะหรือมุมมองที่มีความหมายจริง
- ค้นหาอยู่ใน Filter ของ Tab นั้น ช่องค้นหาเมนูรองมีเฉพาะเมื่อจำเป็นและต้องบอกหน้าที่ต่างกันชัดเจน
- ทุกหน้ารายการมี Filter ที่เหมาะกับข้อมูล ไม่ยัดตัวเลือกเหมือนกันทุกหน้า
- Filter เริ่มต้นแสดงข้อมูลตามสิทธิ์; “ทั้งหมด” หมายถึงทั้งหมดที่ผู้ใช้มีสิทธิ์เห็น
- ไม่แสดง Filter สถานะซ้ำเมื่อ Tab คัดสถานะนั้นแน่นอนแล้ว
- Dashboard เริ่มจากช่วงเวลาและค้นหาเมื่อมีข้อมูลที่ค้นได้ เพิ่ม Filter อื่นเมื่อมีเหตุผลใน Specs รายหน้า
- ข้อความค้นหาไม่ใช้แทนตัวกรองทุกกรณี เช่น ช่วงวัน คลัง และสถานะมีความหมายเฉพาะ แต่ต้องหลีกเลี่ยงช่องซ้ำที่ไม่จำเป็น
- เปลี่ยน Filter แล้วกลับหน้าแรก แสดงเงื่อนไขที่ใช้อยู่ และมีล้างตัวกรอง
- Export ใช้สิทธิ์ ขอบเขตข้อมูล และ Filter เดียวกับหน้าจอ

### 6.3 หน้าเพิ่ม แก้ และดู

- ใช้ Header & Detail ตามภาพ: หัวหน้า/เส้นทางย้อนกลับ ข้อมูลหลัก รายละเอียด และเอกสารแนบ
- วางปุ่มบันทึก/ยกเลิกให้ตรงแบบ ใช้หน้าดูแบบอ่านอย่างเดียวและแสดงปุ่มแก้ตามสิทธิ์
- แต่ละช่องระบุชื่อ ประเภท จำเป็นหรือไม่ ตัวเลือก ค่าเริ่มต้น Validation และสิทธิ์แก้
- เก็บข้อมูลที่กรอกไว้เมื่อบันทึกไม่ผ่าน และระบุข้อผิดพลาดตรงช่อง
- แสดงสถานะกำลังโหลด ไม่มีข้อมูล ไม่มีผลค้นหา ไม่มีสิทธิ์ บันทึกสำเร็จ และข้อมูลถูกแก้โดยผู้อื่น
- ก่อนออกจากหน้าที่แก้แล้วแต่ยังไม่บันทึกต้องมีทางเลือกกลับไปทำต่อ
- แต่ละหน้าใน Design/Specs ระบุชื่อ Section ครอบ เช่น `Admin / จัดการระบบ / ผู้ใช้งาน`

### 6.4 ขนาดจอและการเข้าถึง

รองรับ Mobile <768px, Tablet 768–1023px, Laptop 1024–1439px และ Desktop ≥1440px ตาม Code Style โดยชื่อ Breakpoint ใน Tailwind ต้องตั้งให้สอดคล้อง ไม่อนุมานจากชื่อ `xl` อย่างเดียว ตารางมีทางเลื่อนอ่านได้ ปุ่มและช่องกรอกใช้คีย์บอร์ดได้ สถานะมีข้อความกำกับสี

- ไม่มี Role, บัญชีผู้ใช้ หรือหน้าใช้งานสำหรับฝ่าย/พนักงานตรวจนับสินค้า
- ผู้ตรวจนับทำงานด้วยเอกสารหรือวิธี Manual นอกระบบ และไม่มีสิทธิ์รับเข้า โอนคลัง จัดส่ง หรือแก้ยอดผ่านเว็บ
- Admin คีย์ผลนับจริงเข้าเว็บเพื่อเทียบกับยอดคงเหลือในระบบ โดยเห็นคลัง, Lot, ยอดในระบบ, ยอดที่นับจริง และผลต่าง
- การคีย์ผลตรวจนับเป็นการตรวจสอบเท่านั้น ไม่ปรับยอด, ไม่สร้าง Stock Ledger, ไม่รับเข้า และไม่โอนคลังโดยอัตโนมัติ
- หากพบผลต่าง วิธีอนุมัติและปรับยอดต้องกำหนดใน Specs คลังภายหลัง; ห้ามใช้ผลนับเป็นคำสั่งปรับยอดเอง

### 7.2 กฎบังคับใช้

- ตรวจทั้ง “ทำคำสั่งนี้ได้หรือไม่” และ “ทำกับข้อมูลรายการนี้ได้หรือไม่” ที่ฝั่ง Server
- Sales ใช้ผู้ดูแลลูกค้าและเจ้าของเอกสารในการจำกัดข้อมูล รวมถึง Dashboard, API, Export และ PDF
- ซ่อนต้นทุนจากข้อมูลที่ส่งไป Sales จริง ไม่ส่งไปแล้วเพียงซ่อนคอลัมน์
- Role/Permission เก็บในฐานข้อมูลธุรกิจ ไม่เชื่อคำสั่ง Role ที่ส่งจาก Browser หรือ Metadata ที่ผู้ใช้แก้ได้
- `/admin` เป็นเส้นทางหน้า Back-office ตาม Code Style ไม่ได้แปลว่าผู้เข้าหน้านั้นเป็น Admin ทุกคน
- ผู้ถูกระงับหรือลบต้องถูกปฏิเสธการใช้งานแม้มี Session เดิม
- การเปลี่ยนสิทธิ์มีผลต่อคำขอถัดไปตามกลไกที่กำหนด; ไม่ปล่อยสิทธิ์เดิมค้างเพราะ Cache ไม่จำกัดเวลา
- สิทธิ์ที่ยังไม่มีข้อสรุปต้องไม่เปิดเพิ่มโดยเดา

## 9. ลูกค้า

- เก็บชื่อร้าน/บริษัท ประเภทลูกค้า เลขภาษี ผู้ติดต่อ โทรศัพท์ อีเมล ที่อยู่ออกเอกสารและที่อยู่จัดส่ง
- สร้างรหัสลูกค้าอัตโนมัติแนว `P-YY-MM-ลำดับ` โดยไม่ซ้ำ; รูปแบบปีและจำนวนหลักอยู่ใน OPEN-04
- แนบใบอนุญาตขายยา หนังสือรับรอง และเอกสารที่กำหนด พร้อมวันหมดอายุเมื่อมี
- ระบุพนักงานขายผู้ดูแลและเงื่อนไขชำระเงิน: เงินสด / 30 / 60 / 90 วัน
- Admin เปลี่ยนผู้ดูแลได้และเก็บประวัติ; Sales เห็นเฉพาะข้อมูลในความรับผิดชอบ
- หน้ารายการมีค้นหา สถานะ และตัวกรองประเภท/จังหวัด/เขตที่จำเป็น
- หน้าเดียวเข้าถึงข้อมูลทั่วไป เอกสาร งานขาย และยอดเกี่ยวข้องตามสิทธิ์
- ต้องกำหนดผลต่อเอกสารเก่าเมื่อเปลี่ยนผู้ดูแลลูกค้า ไม่ใช้การเปลี่ยนเจ้าของลูกค้าเขียนทับเจ้าของยอดขายย้อนหลัง
- ขั้นตอน Sales ขอเพิ่มลูกค้าและ Manager อนุมัติเป็นประเด็นจากข้อมูลเก่า ยังรอสรุปก่อนพัฒนา

## 10. สินค้าและคลัง

### 10.1 ข้อมูลหลัก

สินค้าเก็บรหัส ชื่อ หมวด หน่วยประจำ ราคาขาย ข้อมูลต้นทุนตามสิทธิ์ รูป และสถานะ ส่วนยอดคงเหลืออยู่ในข้อมูลสต็อกที่แยกตามคลังและ Lot

| คลัง | การใช้ |
|---|---|
| คลังหลัก | สินค้าพร้อมขาย |
| คลังการตลาด | สินค้าแจก ทดลอง และของแถมที่กำหนดให้ใช้คลังนี้ |
| คลังรอทำลาย | สินค้าหมดอายุ ชำรุด หรือถูกกันออกจากการขาย |

- ห้ามรวมยอดสามคลังแล้วใช้เป็นยอดพร้อมขาย
- คลังรอทำลายไม่ใช้เป็นต้นทางขายหรือของแถม
- หน้ารายการใช้ Tab หรือ Filter เลือกคลัง โดยแสดงคลังที่กำลังดูชัดเจน
- แจ้งล็อตใกล้หมดอายุล่วงหน้า 90 วัน; เงื่อนไขวันขอบเขตและการย้ายคลังรอสรุป

### 10.2 เลือกคลังและโอนจากหน้าสินค้า

ตามความต้องการให้ทำงานกระชับ:

1. ตอนสร้างสินค้า เลือกคลังเริ่มต้นและกรอกยอดเริ่มต้นได้เมื่อมีสิทธิ์และข้อมูล Lot ครบ
2. ถ้ามียอดเริ่มต้น ระบบบันทึกรายการรับยอดเริ่มต้นและ Ledger; ถ้าไม่มี ไม่สร้างยอดจากการเลือกคลังอย่างเดียว
3. ตอนแก้สินค้า มีคำสั่งโอนคลังในหน้าหรือหน้าต่างเดียวกัน เลือกต้นทาง ปลายทาง Lot และจำนวนเต็ม
4. การโอนหักคลังต้นทางและเพิ่มปลายทางพร้อมบันทึกเอกสารอ้างอิงในธุรกรรมเดียว
5. ไม่ใช้การเปลี่ยน `warehouse_id` ของสินค้าเพื่อย้ายยอดทั้งหมดโดยไม่มีประวัติ
6. การแก้ชื่อ/ราคา/รูปสินค้าไม่เปลี่ยนยอดคงเหลือ

### 10.3 กฎรักษายอด

- Lot และวันหมดอายุเชื่อมกับสินค้า; ยอดแต่ละคลังอ้าง Lot เดียวกันเมื่อโอน
- รับเข้า จ่ายออก และโอนต้องมีรายการความเคลื่อนไหวและผู้ทำ
- ตรวจจำนวนเต็มมากกว่าศูนย์และจำนวนต้นทางเพียงพอจาก DB ตอนยืนยันจริง
- ป้องกันการจ่ายพร้อมกันเกินยอดและการกดย้ำทำให้เกิดรายการซ้ำ
- Ledger ที่ยืนยันแล้วไม่ให้แก้จำนวนทับ การกลับรายการต้องอ้างรายการเดิม
- หากมีระบบจองต้องแยกยอดคงเหลือ/จอง/พร้อมใช้ และกำหนดจังหวะจอง/คืนจองก่อนพัฒนา
- จังหวะตัดสต็อก วิธีเลือก Lot, การคืนสินค้าและการทำลายจริงอยู่ใน OPEN-03/11

### 10.4 ตรวจนับสินค้าแบบ Manual

1. ผู้ตรวจนับนับสินค้าและ Lot ด้วยมือภายนอกระบบ
2. Admin สร้างหรือเปิดรอบตรวจนับ แล้วคีย์จำนวนที่นับจริงแยกตามคลังและ Lot
3. ระบบดึงยอด ณ เวลาที่กำหนดมาเปรียบเทียบ และแสดงผลต่างเป็น `ยอดที่นับจริง - ยอดในระบบ`
4. Admin บันทึกผลตรวจนับพร้อมผู้คีย์ เวลา และหมายเหตุเมื่อมี; เก็บ Audit Log
5. ผลต่างเป็นข้อมูลตรวจสอบ ไม่ทำให้ยอดสต็อกหรือ Ledger เปลี่ยน จนกว่าจะมีกฎการปรับยอดที่ผู้ใช้อนุมัติ

การตรวจนับไม่เปิดเป็นหน้าให้ฝ่ายคลังใช้งาน และไม่เปลี่ยนให้ผู้ตรวจนับเป็น Role ในระบบ

## 11. จัดซื้อและค่าใช้จ่าย

### 11.1 จัดซื้อและรับเข้า

- เก็บผู้ขาย ใบสั่งซื้อ หัวเอกสารและรายการสินค้า และใบรับเข้าที่อ้างใบสั่งซื้อได้
- การรับระบุคลังปลายทาง สินค้า Lot วันหมดอายุ จำนวนเต็ม และต้นทุนตามสิทธิ์
- บันทึกร่างไม่เพิ่มสต็อก การยืนยันรับเข้าจึงสร้าง Ledger และเพิ่มยอด
- หากรับบางส่วน ต้องรักษายอดสั่ง/รับแล้ว/ค้างรับ; ขอบเขตการรับเกินและการแก้หลังรับต้องกำหนดก่อนพัฒนา
- Filter ตามหน้ารายการ เช่น ค้นหา ช่วงเวลา ผู้ขาย สถานะ และคลัง

### 11.2 ค่าใช้จ่าย

- เก็บค่าอุปกรณ์ ค่าบริการ และค่าใช้จ่ายบริษัทใน `company_expenses` กับหมวดค่าใช้จ่าย
- ข้อมูลขั้นต่ำ: วันที่ หมวด รายละเอียด จำนวนเงิน ผู้รับเงิน/ผู้ขาย เอกสารแนบ สถานะ ผู้บันทึก
- ไม่สร้าง Product ปลอมเพื่อแทนค่าใช้จ่าย และไม่ทำให้ Stock Ledger เปลี่ยน
- รวมมุมมองรายงานกับการเงินได้ โดยสูตรรายงานแยกต้นทุนสินค้ากับค่าใช้จ่ายบริษัทชัดเจน

## 12. ใบเสนอราคาและการอนุมัติ

- หัวเอกสารมีเลข ลูกค้า พนักงานขาย วันที่ ใช้ได้ถึง เงื่อนไขชำระเงิน และสถานะ
- รายละเอียดมีสินค้า จำนวน ราคา ส่วนลด ภาษี ของแถม และยอดสรุปตามกติกาการเงิน
- Sales ทำรายการเฉพาะลูกค้าของตน; ต้นทุนไม่อยู่ในผลตอบกลับที่ Sales อ่านได้
- ส่วนลดพิเศษต้องส่งให้ Manager อนุมัติ/ไม่อนุมัติ; เกณฑ์ส่วนลดรอสรุป
- เก็บผู้ขอ ผู้พิจารณา เวลา ผล และคำอธิบายตามข้อกำหนดรายโมดูล
- ผลอนุมัติผูกกับรุ่นข้อมูล หากเปลี่ยนราคา/จำนวน/ส่วนลด/เงื่อนไขสำคัญต้องยกเลิกผลอนุมัติรุ่นเดิมและพิจารณาใหม่
- ผู้อนุมัติเห็นข้อมูลฉบับที่จะอนุมัติจริง ป้องกันการอนุมัติคนละรุ่นเมื่อแก้พร้อมกัน
- สถานะร่าง รออนุมัติ อนุมัติ ไม่อนุมัติ หมดอายุ และยกเลิกต้องไม่ปะปนกับสถานะส่งเอกสาร
- รายละเอียด Transition ผู้กดแต่ละปุ่ม และเงื่อนไขออก PDF กำหนดใน Specs รายโมดูล

## 13. คำสั่งซื้อและจัดส่ง

- สร้างจากใบเสนอราคาหรือสร้างตามสิทธิ์ โดยเก็บการอ้างอิงต้นทาง
- แยกชนิดรายการสินค้าขายกับของแถม แม้เป็นสินค้าเดียวกัน
- รายการมีจำนวนสั่ง ส่งแล้ว และค้างส่ง พร้อมคลัง/Lot ที่จ่ายจริง
- แยกสถานะคำสั่งซื้อ สถานะจัดส่ง และสถานะชำระเงิน ไม่ใช้ช่องสถานะเดียวแทนทั้งหมด
- รองรับส่งบางส่วนโดยไม่ส่งซ้ำเกินจำนวนสั่ง
- งานจัดส่งและการยืนยันจ่ายในเว็บทำโดย Admin ตามสิทธิ์ที่กำหนด; ไม่มีบัญชีฝ่ายคลังในระบบ
- การยกเลิกต้องจัดการสต็อก/การจอง/การเงินที่เกิดแล้วตามสถานะ ไม่เปลี่ยนข้อความสถานะอย่างเดียว
- การส่งคำสั่งซื้อทั้งหมดให้ Manager อนุมัติยังไม่เป็นกฎยืนยัน ดู OPEN-02
- Filter แยกตามงาน เช่น วันที่ สถานะคำสั่งซื้อ สถานะส่ง ลูกค้า และเลขอ้างอิง

## 14. การเงิน

### 14.1 ตั้งหนี้ วางบิล และรับชำระ

- แยกยอดตั้งหนี้ออกจากเอกสารรวมวางบิล เพื่อไม่เกิดหนี้ซ้ำเมื่อพิมพ์หรือรวมบิล
- เอกสารมีวันออก วันครบกำหนด ยอดตั้งหนี้ ยอดรับชำระ และยอดคงค้าง
- เงื่อนไขชำระเงินมีเงินสด/30/60/90 วัน และบันทึกค่าที่ใช้บนเอกสารนั้น
- รับชำระบางส่วนได้หลายครั้ง เก็บวันที่ ช่องทาง จำนวนเงิน หลักฐาน และผู้บันทึก
- แยก `payments` กับ `payment_allocations` เพื่อรองรับหนึ่งการรับชำระตัดหลายบิล และหนึ่งบิลรับชำระหลายครั้ง
- รวมยอดจัดสรรไม่เกินยอดรับชำระ และไม่ทำยอดหนี้ติดลบจากการจัดสรรปกติ
- ยอดเกิน เงินมัดจำ การคืนเงิน และการแก้รับชำระที่ปิดแล้วต้องสรุปกติกาก่อนเพิ่มฟังก์ชัน
- การรับเงิน/จัดสรร/กลับรายการมี Audit Log และป้องกันการบันทึกซ้ำ

### 14.2 ลูกหนี้และการแจ้งเตือน

- ยอดคงค้างคำนวณจากรายการหนี้และการจัดสรรที่มีผล ไม่กรอก Aging ด้วยมือ
- ใช้วันครบกำหนดเป็นฐานอายุหนี้ พร้อมระบุวันที่ใช้คำนวณรายงาน
- มีแถบหรือ Tab สีแดงพร้อมข้อความสำหรับเกินกำหนด 90 และ 120 วัน
- ต้องตกลงความหมาย “ครบ 90 วัน” หรือ “มากกว่า 90 วัน” ใน Specs การเงิน แล้วใช้สูตรเดียวทุกหน้า
- Filter สำคัญ: ค้นหา ช่วงวัน ลูกค้า สถานะชำระ และช่วงอายุหนี้; ไม่ต้องแสดงซ้ำกับ Tab
- การแจ้งเตือนหนี้ไม่หมายความว่าบล็อกการขายอัตโนมัติ จนกว่าจะมีกฎยืนยัน

## 15. โปรโมชันและของแถม

- Manager เป็นผู้กำหนดและอนุมัติตามกฎธุรกิจเดิม Sales เลือกใช้ได้เฉพาะรายการที่อนุมัติและอยู่ในช่วงใช้งาน
- เงื่อนไขมีช่วงเวลา สินค้าที่ร่วม จำนวน/มูลค่าที่เข้าเงื่อนไข และรางวัลหรือของแถมตามแบบที่สรุป
- Sales ไม่แก้เงื่อนไข เพิ่มของแถมเอง หรือแก้จำนวนของแถมข้ามเงื่อนไข
- รายการของแถมมี Product, จำนวนเต็ม, คลังและ Lot เพื่อจ่ายสต็อกจริง
- เอกสารลูกค้าแสดงชื่อ จำนวน หน่วย และคำว่า “ของแถม”; ช่องราคา/ยอดรายการต้องว่างหรือไม่แสดง ไม่พิมพ์ `0.00` เป็นราคา
- มูลค่าขายภายในอาจเป็นศูนย์ แต่ต้นทุนคลังยังมีและไม่เปิดให้ Sales เห็น
- ไม่หักคลังหลักแทนคลังการตลาดโดยอัตโนมัติ กติกาต้นทางของแถมต้องระบุชัดเจน
- เก็บเงื่อนไขโปรโมชันรุ่นที่ใช้กับเอกสาร เพื่อให้เปลี่ยนโปรโมชันแล้วไม่เปลี่ยนยอดเก่า
- สิทธิ์ Admin เทียบกับ “Manager เท่านั้น” และการอนุมัติโปรโมชันตนเองอยู่ใน OPEN-01

## 16. Dashboard และรายงาน

- Dashboard หลักรวมยอดขาย งานที่รอทำ สต็อก และการเงินเฉพาะสิทธิ์ของผู้ใช้
- Sales เห็นยอดและลูกค้าของตน; Manager เห็นภาพรวมตามขอบเขต; บัญชีเห็นการเงิน; Admin เห็นข้อมูลคลังและผลตรวจนับ
- ไม่ต้องสร้าง Dashboard แยกทุกเมนูย่อยหากสรุปรวมในหน้าหรือแท็บได้
- รายงานยอดขายระบุว่าอ้างคำสั่งซื้อ การส่งของ หรือยอดตั้งหนี้ และจัดการยกเลิกอย่างไร
- รายงานต้นทุน/กำไรต้องรอเลือกวิธีคิดต้นทุน ไม่แสดงค่าจำลองเป็นสูตรกำไรจริงที่อนุมัติแล้ว
- รายงานคลังแยกคลัง Lot และช่วงเวลา; Ledger แสดงรายการต้นทางและปลายทาง
- รายงานการเงินระบุวันตัดยอดและนิยามยอดค้างชัดเจน
- การส่งออกมีเงื่อนไขเดียวกับการดู และไม่หลุดข้อมูลข้าม Sales ผ่านยอดรวม/ไฟล์/จำนวนรายการ

## 17. เลขเอกสารและ PDF

### 17.1 เลขอัตโนมัติ

- ทุกเอกสารมี ID ภายในคงเดิม และมีเลขที่เอกสารสำหรับแสดงแยกกัน
- เชื่อมตารางด้วย ID ภายใน ไม่ใช้เลขเอกสารที่แก้ได้เป็น Foreign Key
- ใช้ตัวสร้างเลขกลางที่กันเลขซ้ำเมื่อหลายคนสร้างพร้อมกัน
- เก็บประวัติเลขที่เคยใช้ รวมเลขยกเลิก เพื่อไม่จ่ายเลขนั้นซ้ำ
- รูปแบบ Prefix, ปี ค.ศ./พ.ศ., การเริ่มลำดับใหม่ และขอบเขต Unique อยู่ใน Specs เอกสาร

### 17.2 Admin แก้เลขด้วยมือ

1. Admin แก้เลขแล้วกด **บันทึก**
2. ระบบแสดงรายการที่จะเปลี่ยน เลขเดิม เลขใหม่ และข้อมูลอ้างอิงสำคัญ
3. Admin กด **ยืนยันบันทึก** จึงเขียนข้อมูลจริง หรือกดยกเลิกเพื่อกลับไปแก้
4. ตอนยืนยัน Server ตรวจสิทธิ์ เลขซ้ำ และรุ่นข้อมูลอีกครั้ง
5. บันทึก Audit Log ผู้ทำ เวลา เลขเดิมและเลขใหม่ **ไม่ต้องกรอกเหตุผล และไม่เพิ่มช่องเหตุผลในขั้นตอนนี้**
6. กดยืนยันซ้ำไม่เกิดการแก้หรือออกเอกสารซ้ำ

การยืนยันสองจังหวะเป็น UX ของการเปลี่ยนเลข ไม่ใช่การเพิ่มผู้อนุมัติอีกคนหรือระบบขออนุมัติเลขเอกสาร PDF เดิมยังคงอยู่ รุ่นใหม่ใช้เลขใหม่ เงื่อนไขเอกสารที่ปิดแล้วต้องระบุใน OPEN-04 ก่อนพัฒนา

### 17.3 PDF รุ่นแรก

| เอกสาร | ข้อมูลหลัก | เงื่อนไข |
|---|---|---|
| ใบเสนอราคา | ลูกค้า รายการ ราคา ส่วนลด เงื่อนไข ใช้ได้ถึง | เมื่อขอส่วนลดพิเศษ ต้องใช้ผลอนุมัติของรุ่นข้อมูลปัจจุบัน |
| ใบยืนยันคำสั่งซื้อ | ลูกค้า รายการ จำนวน นัดส่ง เงื่อนไข | อ้างคำสั่งซื้อและรุ่นข้อมูล |
| ใบส่งของ | ผู้รับ ที่อยู่ สินค้า/ของแถม จำนวนส่งจริง | อ้างการส่งครั้งนั้น ไม่ใช้ยอดสั่งทั้งหมดเมื่อส่งบางส่วน |
| ใบวางบิล | เอกสารที่นำมาวางบิล ยอด และกำหนดชำระ | ไม่สร้างหนี้ซ้ำจากการพิมพ์ |
| ใบรับชำระเงิน | วันที่ ช่องทาง ยอดรับ บิลที่จัดสรร | ไม่แสดงว่า “ชำระครบ” ถ้ายังมียอดค้าง |

- ใช้แบบเอกสาร Logo Font และข้อความบริษัทที่ผู้ใช้ส่ง
- รองรับภาษาไทย พ.ศ. ตารางหลายหน้า และการขึ้นหน้าที่ไม่ตัดหัว/ท้ายผิดตำแหน่ง
- เก็บประเภทเอกสาร ID รุ่นข้อมูล รุ่น Template ผู้สร้าง และเวลาสร้าง
- PDF ที่ออกแล้วเก็บ Snapshot ของข้อมูลที่ใช้ ไม่เปลี่ยนย้อนหลังเมื่อชื่อ/ที่อยู่/สินค้าเปลี่ยน
- หน้ารุ่น Mock และ PDF จำลองต้องบอกว่าเป็นข้อมูลจำลอง ไม่ทำให้เข้าใจว่าเป็นเอกสารจริง
- ต้องกำหนดข้อความ “ตัวอย่าง” และตำแหน่งใน Template ร่วมกับผู้ใช้

## 18. สถาปัตยกรรมเว็บและ API

### 18.1 เส้นทางข้อมูล

```text
หน้าเว็บ / Components
  → src/service/http.ts
  → Next.js API
  → ตรวจตัวตน + สิทธิ์ + ขอบเขตข้อมูล + Validation
  → บริการธุรกิจฝั่ง Server
  → Prisma → PostgreSQL

Auth Service → Supabase Auth
File Service → Supabase Storage
PDF Service → สร้างเอกสารและบันทึกไฟล์/รุ่น
```

- Next.js ดูแลทั้งหน้าเว็บและ API ไม่แยก Backend framework ในรุ่นแรก
- Prisma และข้อมูลลับอยู่ฝั่ง Server เท่านั้น
- หน้าเว็บไม่ติดต่อ DB ธุรกิจโดยตรงและไม่เขียนตารางผ่าน Supabase Data API ข้ามกฎธุรกิจ
- ใช้ Auth Service และ File Service กลาง ไม่กระจาย SDK ลงในทุกหน้า
- Cookie Session ตรวจสอบกับ Auth ที่เชื่อถือได้ก่อนใช้ ข้อมูลสิทธิ์อ่านจากระบบธุรกิจ; Middleware/Proxy ช่วยเรื่อง Session แต่ไม่แทนการตรวจใน API

Supabase มีแนวทาง SSR แบบ Cookie และชื่อ Middleware/Proxy ต่างกันตามรุ่น Next.js จึงเลือกวิธีที่ตรงรุ่นที่ล็อกตอนทำ Plan: [เอกสาร Supabase SSR](https://supabase.com/docs/guides/auth/server-side/creating-a-client?queryGroups=framework&framework=nextjs)

### 18.2 API Contract

Specs รายโมดูลต้องระบุคำสั่ง รับข้อมูลอะไร ส่งกลับอะไร สิทธิ์ ขอบเขตข้อมูล ผลต่อ DB/Audit และกรณีผิดพลาด โดยชื่อ Endpoint ยังไม่ล็อกในเอกสารระดับโครงการ

- รายการรองรับ `search`, Filter แบบระบุชนิด, การเรียง และ Pagination พร้อมยอดรวมตามสิทธิ์
- จำกัดฟิลด์ที่แก้ได้และฟิลด์ที่ส่งกลับ; ไม่รับทุกช่องจาก Body มาเขียน DB อัตโนมัติ
- ตรวจข้อมูลจำเป็น รูปแบบ ค่าไม่ซ้ำ จำนวนเต็ม และข้อจำกัดตามสถานะที่ Server
- ข้อผิดพลาดแยกไม่เข้าสู่ระบบ ไม่มีสิทธิ์ ไม่พบข้อมูล ข้อมูลไม่ถูกต้อง และข้อมูลเปลี่ยนพร้อมกัน
- ส่งข้อความภาษาไทยที่ผู้ใช้แก้ตามได้ พร้อมชื่อช่องเมื่อเกี่ยวข้อง
- การแก้ข้อมูลใช้ตัวระบุรุ่น เช่น `version` เพื่อป้องกันการเขียนทับงานล่าสุดโดยไม่รู้ตัว
- คำสั่งที่มีผลต่อเงิน/สต็อก/เลขเอกสารมีรหัสคำขอหรือข้อบังคับ Unique เพื่อกันการทำซ้ำ
- ยอดและสิทธิ์สำคัญคำนวณใหม่บน Server ไม่เชื่อค่ารวมที่ Browser ส่งมา
- การเข้าถึง DB ผ่าน Prisma ไม่ถือว่าได้รับ RLS ตาม Session โดยอัตโนมัติ ต้องระบุกลไกสิทธิ์และ Context ของการเชื่อมต่อให้ชัด

### 18.3 Auth และการย้ายผู้ให้บริการ

- `users.id` เป็นผู้ใช้งานภายในคงที่ ตารางธุรกิจอ้างรหัสนี้
- `auth_accounts` เชื่อมผู้ใช้กับคู่ `provider` และ `provider_user_id` ซึ่งต้องไม่ซ้ำ
- Supabase Auth ดูแลรหัสผ่าน Session และ Reset Password; ระบบไม่เก็บรหัสผ่านหรือ Hash ซ้ำใน users
- Role/Permission/สถานะพนักงานเก็บใน DB ธุรกิจ
- การระงับใช้กฎฝั่ง API กับผู้ใช้ภายใน ไม่อาศัยการซ่อนเมนูหรือรอ Token หมดอายุอย่างเดียว
- ย้าย DB ธุรกิจโดยคง Auth เดิมได้ตามสถาปัตยกรรมนี้ แต่หากเลิกใช้ Supabase ต้องวางงานย้าย Auth/Session/ไฟล์ด้วย
- การย้ายไป DB คนละชนิดต้องตรวจชนิดข้อมูล SQL, Audit Trigger, Constraint และ Migration ใหม่ ไม่ถือว่าเปลี่ยน Connection String แล้วเสร็จ

### 18.4 ไฟล์

- DB เก็บ Provider, Bucket, Object Key, ชื่อเดิม, ชนิด, ขนาด, ผู้แนบ เวลา และข้อมูลธุรกิจที่เกี่ยวข้อง
- ไม่เก็บ URL ที่หมดอายุเป็นตัวอ้างอิงถาวร
- เอกสารธุรกิจเป็น Private และตรวจสิทธิ์ก่อนเปิด/ดาวน์โหลด
- ตรวจประเภทและขนาดไฟล์ตาม Specs รายโมดูล และจัดการไฟล์แนบที่อัปโหลดสำเร็จแต่บันทึก DB ไม่สำเร็จ
- การลบเชิงตรรกะไม่ลบไฟล์ที่เอกสารย้อนหลังยังอ้างอิง
- หากฝั่ง Server ใช้สิทธิ์ Storage ที่สูง ต้องตรวจสิทธิ์ของผู้ใช้ก่อนทุกคำสั่ง; ไม่ส่ง Key นั้นให้ Browser

กลไกควบคุมสิทธิ์ Storage ต้องสอดคล้องกับสิทธิ์ของระบบ: [Supabase Storage Access Control](https://supabase.com/docs/guides/storage/security/access-control)

## 19. โครงสร้างฐานข้อมูล

> ส่วนนี้เป็นแบบข้อมูลเชิงตรรกะให้ตรวจ ยังไม่ใช่ Prisma Schema หรือ SQL ที่พร้อมรัน ชื่อตารางปรับได้ใน Specs รายโมดูลโดยเก็บ Mapping และเหตุผล

### 19.1 หลักร่วม

- ตารางที่มีตัวตนถาวรใช้ ID ภายใน แยกจากรหัสลูกค้า รหัสสินค้า และเลขเอกสาร
- ตารางแก้ไขได้มีผู้สร้าง/เวลา ผู้แก้/เวลา และรุ่นข้อมูลตามความจำเป็น
- เก็บการอ้างอิงจริงด้วย Foreign Key หรือกลไกเทียบเท่า ไม่อาศัยชื่อข้อความเชื่อม
- ข้อมูลหัวเอกสารและรายการแยกกันตาม Header & Detail
- ข้อมูลเดิมของลูกค้า สินค้า ราคา ภาษี และเงื่อนไขที่ใช้ในเอกสารเก็บ Snapshot ตามรุ่น
- เงินใช้ Decimal; วันที่ธุรกิจใช้ Date; เหตุการณ์ใช้ Timestamp; Quantity ใช้ Int
- เลขภาษี โทรศัพท์ รหัส และเลขเอกสารเก็บเป็นข้อความเพื่อคงเลขศูนย์ด้านหน้า
- JSON ใช้กับ Audit Diff/Snapshot/ค่าเฉพาะที่กำหนดชนิดแล้ว ไม่ใช้แทนความสัมพันธ์ธุรกิจหลักทั้งหมด

### 19.2 ตารางและความสัมพันธ์หลัก

| กลุ่ม | ตารางเชิงตรรกะ | ข้อมูล/ความสัมพันธ์ |
|---|---|---|
| บัญชีภายใน | `users`, `auth_accounts` | users 1:N auth_accounts; คู่ Provider/User ID ไม่ซ้ำ |
| สิทธิ์ | `roles`, `permissions`, `user_roles`, `role_permissions` | เชื่อมผู้ใช้กับบทบาทและคำสั่ง; UI การมีหลาย Role รอ Specs ผู้ใช้ |
| ทีม/เขต | `sales_teams`, `sales_territories`, ตารางสมาชิกเมื่อใช้ | ข้อมูลอ้างอิงเพื่อจัดความรับผิดชอบ ไม่เพิ่มสิทธิ์เอง |
| ตั้งค่า | `company_profiles`, `system_settings` | ข้อมูลบริษัทและค่ากลางมีชนิดข้อมูล/รุ่น/ประวัติ |
| เลขเอกสาร | `document_sequences`, `document_number_history` | ลำดับเลขและเลขที่ใช้แล้ว อ้างเอกสารภายใน |
| ประวัติ | `audit_logs` | ผู้ทำ เหตุการณ์ ตาราง รายการ ก่อน/หลัง Request ID รุ่น Schema |
| ไฟล์ | `files`, ตารางเชื่อมไฟล์เฉพาะโมดูล | ข้อมูลไฟล์และความสัมพันธ์ที่ตรวจสิทธิ์ได้ |
| ลูกค้า | `customers`, `customer_contacts`, `customer_addresses` | ลูกค้า 1:N ผู้ติดต่อ/ที่อยู่ |
| เอกสารลูกค้า | `customer_documents` | ลูกค้า → ไฟล์ ประเภทเอกสาร วันหมดอายุ |
| ผู้ดูแลลูกค้า | `customer_sales_assignments` | ประวัติผู้ดูแลและช่วงเวลาที่มีผล |
| เงื่อนไขเงิน | `payment_terms` | เงินสด/30/60/90 วัน; เอกสารเก็บ Snapshot เงื่อนไขที่ใช้ |
| สินค้า | `products`, `product_categories`, `product_units` | สินค้า → หมวดและหน่วยประจำ; ไม่มี Conversion |
| คลังและ Lot | `warehouses`, `inventory_lots` | คลังสามประเภท; Lot ผูก Product และวันหมดอายุ |
| ยอดสต็อก | `inventory_balances` | Unique ต่อคลัง+Lot; Product ได้จาก Lot |
| ตรวจนับ Manual | `stock_count_sessions`, `stock_count_items` | Admin บันทึกรอบและยอดนับจริงเพื่อเทียบกับยอดระบบ; ไม่มีผลต่อยอดคงเหลือหรือ Ledger |
| ความเคลื่อนไหว | `stock_movements` | Lot คลัง จำนวนมีทิศทาง ประเภท และเอกสารต้นทาง |
| โอนคลัง | `stock_transfers`, `stock_transfer_items` | หัวโอน → รายการ Lot/จำนวน → รายการออกและเข้า |
| จองสินค้า (ถ้ายืนยัน) | `stock_reservations` | อ้าง Order/Lot/คลัง/จำนวน ไม่รวมเป็นยอดคงเหลือใหม่ |
| ผู้ขาย | `suppliers` | ผู้ขายสำหรับจัดซื้อ และอ้างในค่าใช้จ่ายได้ |
| จัดซื้อ | `purchase_orders`, `purchase_order_items` | หัวใบสั่งซื้อ 1:N รายการสินค้า |
| รับเข้า | `goods_receipts`, `goods_receipt_items` | หัวรับเข้า → รายการ → Ledger; อ้าง PO ตามกรณี |
| ค่าใช้จ่าย | `expense_categories`, `company_expenses` | แยกจาก products; แนบไฟล์และอ้างผู้ขายได้ |
| เสนอราคา | `quotations`, `quotation_items` | ลูกค้า/เจ้าของ → หัวเอกสาร → รายการ/ของแถม |
| อนุมัติ | `quotation_approvals`, `promotion_approvals` | เก็บรุ่นที่ขอและผลตัดสิน; ชนิดอนุมัติอื่นเพิ่มเมื่อยืนยัน |
| คำสั่งซื้อ | `sales_orders`, `sales_order_items` | อ้าง Quotation ได้; รายการมีชนิดขาย/ของแถม |
| จัดส่ง | `deliveries`, `delivery_items` | อ้าง Order Item และ Lot ที่จ่าย แยกการส่งแต่ละครั้ง |
| ตั้งหนี้ | `invoices`, `invoice_items` | หนี้และรายการอ้างงานขาย; ชื่อนี้ไม่หมายถึงใบกำกับภาษีในรุ่นแรก |
| วางบิล | `billing_notes`, `billing_note_items` | รวม Invoice ในใบวางบิล ไม่สร้างยอดหนี้ใหม่ |
| รับชำระ | `payments`, `payment_allocations` | จัดสรรจำนวน Decimal ระหว่าง Payment และ Invoice |
| โปรโมชัน | `promotions`, `promotion_conditions`, `promotion_rewards` | เงื่อนไข/รางวัล/ช่วงเวลา/รุ่นอนุมัติ |
| การใช้โปรโมชัน | `order_promotions` หรือข้อมูลอ้างอิงเฉพาะรายการ | เชื่อม Order/รุ่นโปรโมชัน/รายการของแถมที่เกิดจริง |
| เอกสารที่ออก | `document_versions` | ประเภท ID เอกสาร รุ่นข้อมูล Snapshot รุ่น Template และไฟล์ PDF |
| การนำเข้าในอนาคต | `import_batches`, `legacy_mappings` | ระบุ Source/รหัสเก่า/IDใหม่/ผลการนำเข้าเมื่อเริ่มงานย้ายจริง |

ไม่สร้าง `receivable_aging` เป็นตารางให้กรอกยอดเอง และไม่สร้าง `order_free_items` ซ้ำกับรายการของแถมใน Order จนทำให้ตัดสต็อกสองครั้ง ผลรวมรายงานและการแจ้งเตือนใช้ Query/View หรือข้อมูลสรุปที่สร้างใหม่ได้ตามความจำเป็น

### 19.3 สิ่งที่ต้องเป็นธุรกรรมเดียวกัน

| การทำรายการ | สิ่งที่ต้องสำเร็จร่วมกัน |
|---|---|
| รับสินค้า | สถานะรับเข้า รายการรับ Ledger ยอดคงเหลือ Audit |
| โอนคลัง | หัว/รายการโอน จ่ายออก รับเข้า ยอดทั้งสองคลัง Audit |
| ยืนยันจ่าย | สถานะจ่าย รายการ/Lot Ledger ยอดคงเหลือ และการปลดจองถ้ามี |
| รับชำระ | Payment การจัดสรร ยอด/สถานะที่เกี่ยวข้อง และ Audit |
| อนุมัติ | ผลพิจารณา รุ่นข้อมูลที่อนุมัติ และสถานะเอกสาร |
| เปลี่ยนเลข | ตรวจรุ่น/Unique เลขใหม่ ประวัติเลข และ Audit |

DB Transaction ครอบคลุมการเขียน DB ส่วนการสร้างบัญชี Auth, อัปโหลดไฟล์ และสร้าง PDF ต้องมีสถานะงาน/Retry/การแก้ผลค้าง เพราะไม่สามารถถือว่าเป็นธุรกรรมเดียวกับ PostgreSQL โดยอัตโนมัติ

### 19.4 การเปลี่ยน Schema

- เปลี่ยนผ่าน Prisma Migration เป็นทางหลัก SQL สำหรับ Trigger/Constraint อยู่ในชุด Migration เดียวกัน
- ไม่ใช้หลายระบบ Migration แข่งกันเขียน Schema เดียวโดยไม่มีเจ้าของ
- Migration ที่ใช้แล้วไม่แก้ทับ; เพิ่ม Migration ใหม่และระบุผลต่อข้อมูลเก่า
- ก่อนลด/ลบคอลัมน์ ให้กำหนดการย้ายข้อมูล Backup และวิธีกู้คืน
- การเพิ่มข้อมูลอ้างอิง เช่น หมวดสินค้า ใช้ข้อมูลในตารางเมื่อเหมาะสม ไม่แก้ Code ทุกครั้ง
- ทุก Schema change ต้องตรวจผลต่อ API, Forms, Seed, Audit, PDF, Export และเอกสาร
- รายงานว่าข้อมูลเพิ่ม/ลดได้ผ่านกระบวนการนี้ ไม่หมายถึงลบโครงสร้างโดยไม่มีผลต่อข้อมูลเดิม

## 20. ประวัติการเปลี่ยนข้อมูล

### 20.1 ความครอบคลุม

คำว่า “ทุกตาราง” ครอบคลุมตารางธุรกิจและตารางประกอบที่แอปดูแล รวมลูกค้า สินค้า รายการย่อย ตารางเชื่อม Roles/Permissions Settings, ไฟล์ Metadata และการเปลี่ยนสถานะ ไม่จำกัดเฉพาะตารางสำคัญ

- `audit_logs` เป็นประวัติแบบเพิ่มรายการ ห้าม Audit ตัวเองจนวนซ้ำ
- ตารางของ Supabase Auth/Storage และตารางระบบ Migration ต้องระบุรายการและเจ้าของแยก ใช้ประวัติของบริการและเหตุการณ์ที่แอปเป็นผู้สั่ง ไม่อ้างว่ามี Trigger ของแอปครอบคลุมโดยยังไม่ตรวจ
- เก็บบัญชีรายการตารางพร้อม `วิธีบันทึกประวัติ / เหตุการณ์ที่รองรับ / ข้อยกเว้น` ก่อนส่งมอบงาน DB
- ข้อยกเว้นต้องระบุเหตุผลและให้ผู้ใช้ตรวจ ไม่ยกเว้นตารางธุรกิจใหม่โดยเงียบ ๆ

### 20.2 รูปแบบข้อมูล

| เหตุการณ์ | ประวัติที่ต้องเก็บ |
|---|---|
| เพิ่ม | ค่าที่สร้างของฟิลด์ธุรกิจที่อนุญาตให้บันทึก |
| แก้ | ฟิลด์ที่เปลี่ยน พร้อมค่าก่อน/หลัง |
| ลบเชิงตรรกะ/กู้คืน | ตัวรายการ ผู้ทำ เวลา สถานะก่อน/หลัง เหตุผลตามประเภทคำสั่ง |
| ยกเลิกธุรกรรม | สถานะและข้อมูลอ้างอิงการกลับรายการ เหตุผลตามกติกาโมดูล |
| อนุมัติ/ไม่อนุมัติ | ผล ผู้พิจารณา รุ่นข้อมูล และคำอธิบายตามกติกา |
| เปลี่ยนเลขเอกสาร | เลขเดิม/ใหม่ ผู้ทำ เวลา รุ่นข้อมูล; ไม่บังคับเหตุผล |
| เหตุการณ์สำคัญ | Snapshot เพิ่ม เช่น ออกเอกสารและการตัดสินอนุมัติ |

ทุกเหตุการณ์มี ID, เวลา, ผู้ทำ/ระบบงาน, Role ขณะทำ, ตาราง/รายการ, ประเภทคำสั่ง, Request ID และรุ่นโครงสร้างข้อมูลที่ใช้ตีความประวัติ

### 20.3 กลไกและข้อจำกัด

- ใช้ Trigger สำหรับตารางธุรกิจที่ต้องรับประกันประวัติระดับ DB ร่วมกับข้อมูลผู้ทำจาก Server
- ส่งผู้ทำในขอบเขต Transaction ของคำขอนั้น เพื่อไม่หลงผู้ใช้เมื่อใช้ Connection Pool
- การแก้ตรง DB โดยผู้ดูแลต้องระบุผู้ทำหรือถูกบันทึกเป็น Database/System Actor ไม่อ้างชื่อผู้ใช้งานที่ไม่ทราบ
- หากบันทึก Audit ของธุรกรรมที่กำหนดว่าต้องมีไม่สำเร็จ ให้ธุรกรรมนั้นไม่สำเร็จด้วย
- ห้ามบันทึกรหัสผ่าน Password Hash, Token, Secret หรือข้อมูลลับลง Before/After
- การเข้าดูประวัติต้องคุมสิทธิ์และปิดต้นทุนจาก Sales เช่นเดียวกับหน้าข้อมูลหลัก
- การเก็บประวัติไม่ได้เท่ากับการสำรองข้อมูล และไม่ได้อนุญาตย้อนคืนธุรกรรมการเงิน/คลังอัตโนมัติ
- ระยะเก็บ ปริมาณ และการ Archive รอสรุป; ระหว่างนี้ไม่มีงานล้างประวัติอัตโนมัติ

## 21. การลบและกู้คืน

- ข้อมูลหลักใช้ `deleted_at`, `deleted_by`, `delete_reason` ตามประเภทข้อมูล
- หน้าปกติไม่แสดงรายการที่ลบ แต่เอกสารเก่ายังอ่านข้อมูลที่อ้างอิงได้
- Admin เปิดรายการที่ลบแล้ว ค้นหา กรอง ดูผู้ลบ/เวลา/เหตุผล และกู้คืนผ่านเว็บ
- การกู้คืนตรวจ Unique และความพร้อมของข้อมูลอ้างอิงก่อน พร้อมระบุเหตุผลและ Audit
- การระงับผู้ใช้ต้องทำให้บัญชีภายในหมดสิทธิ์ ไม่ลบประวัติผู้สร้างเอกสาร
- เอกสารธุรกรรมใช้สถานะยกเลิกและผลกลับรายการ ไม่ Hard Delete เอกสารและ Ledger ที่ยืนยันแล้ว
- เลขเอกสารและรหัสที่ประวัติยังใช้อ้างอิงต้องไม่ถูกแจกซ้ำ
- การลบถาวร/ล้างประวัติ/ล้างไฟล์จำนวนมากเป็นงานแยก ไม่อยู่ในปุ่มลบทั่วไป

## 22. Mock Data และการย้ายระบบ

### 22.1 ข้อมูลจำลอง

- Seed ลง PostgreSQL จริง ใช้ API และกฎเดียวกับงานจริง ไม่ให้หน้าเว็บอ่านชุด Hardcode แทน DB ธุรกิจ
- Seed แยกตามโมดูลและมีรุ่นที่อ้างอิง Schema ได้
- สร้างซ้ำโดยไม่เพิ่มรายการเดิมซ้ำ และไม่ล้างข้อมูลที่ผู้ใช้กรอกเองโดยอัตโนมัติ
- คำสั่ง Reset ต้องแยกจาก Seed และใช้เฉพาะฐานข้อมูลทดสอบที่ระบุชัด
- รหัสผ่านบัญชีจำลองมาจาก Environment/ขั้นตอนตั้งค่าเฉพาะเครื่อง ไม่ Commit เป็นรหัสใช้งานจริง
- ใช้ข้อมูลสมมุติที่ไม่อ้างบุคคลหรือบริษัทจริง พร้อมป้าย “ข้อมูลจำลอง”

### 22.2 กรณีจำลองขั้นต่ำ

- ผู้ใช้ครบ 5 Roles และ Sales อย่างน้อยสองคนเพื่อทดสอบขอบเขตข้อมูล
- ลูกค้าต่างผู้ดูแล ครบเงื่อนไขเงินสด/30/60/90 วัน และเอกสารแนบตัวอย่าง
- สินค้าต่างหมวด หน่วยคงที่ หลาย Lot และยอดแยกสามคลัง
- Lot ปกติ ใกล้หมดอายุ จุดขอบเขต 90 วัน หมดอายุ และชำรุด
- สินค้าหมด/ยอดไม่พอ และกรณีโอนบางส่วน
- ใบเสนอราคาร่าง รออนุมัติ อนุมัติ ไม่อนุมัติ และแก้หลังอนุมัติ
- คำสั่งซื้อมีของแถม ส่งบางส่วน และส่งครบ
- หนี้ยังไม่ครบกำหนด เกิน 90/120 วัน รับบางส่วน รับครบ และยกเลิกรับชำระ
- ข้อมูลถูกลบ กู้คืน และรหัสที่ชนเมื่อกู้คืน
- Audit Diff/Snapshot และเอกสาร PDF ครบชนิด

### 22.3 เตรียมข้อมูลจริงภายหลัง

- ยังไม่ทราบ Schema/ไฟล์ส่งออกจากเว็บเก่า จึงไม่กำหนด Mapping สมมุติเป็นของจริง
- โครงใหม่ไม่ต้องใช้ชื่อ Table/Field/Variable เหมือนเก่า
- ใช้รหัสภายในคงเดิมและเตรียม Mapping จาก `source_system + source_entity + legacy_id`
- เมื่อได้ข้อมูลจริงต้องมีข้อกำหนดแปลงข้อมูล ตรวจซ้ำ รายงานข้อมูลผิด และตรวจยอดก่อน/หลัง
- แยกการย้าย DB ธุรกิจ การย้าย Auth และการย้ายไฟล์เป็นรายการงานที่ตรวจครบได้
- การรับ Mock เข้า Main เป็นเวอร์ชันพร้อมใช้งานของขอบเขต Mock ไม่ใช่อนุญาตให้ใช้ข้อมูลบริษัทจริงทันที

### 22.4 Mock เพื่อเสนอแนวคิดก่อนยืนยันรายละเอียด

- เจ้าของโครงการอนุมัติให้เดินหน้าทำเว็บ Mock สำหรับนำเสนอ แม้ข้อมูลจริงและกฎย่อยบางส่วนยังไม่พร้อม; ใช้ Specs ที่ยืนยันแล้วเป็นหลัก และใช้ข้อเสนอ/ข้อมูลจำลองใน OPEN เป็นแนวทางแสดงหน้าจอชั่วคราวได้
- หน้าจอ Mock ใช้ข้อมูลสมมุติที่ติดป้าย “ข้อมูลจำลอง”; ปุ่มและฟอร์มทำงานเพื่อสาธิตภายในหน้าได้ แต่ไม่สร้าง Auth จริง ไม่บันทึก DB/Storage ไม่ส่งการแจ้งเตือน และไม่ใช้แทน Validation หรือ Permission จริง
- กฎที่ยังไม่ยืนยันให้แสดงเป็นตัวอย่างที่แก้ไขได้ภายหลัง ห้ามอ้างว่าเป็นข้อกฎหมาย/ข้อบังคับของบริษัท และห้ามสร้าง Migration, API หรือ Backend behavior เพื่อบังคับใช้กฎเหล่านั้น
- เมื่อเจ้าของได้ข้อมูลจริง ให้แก้ Specs รายหน้า/Plan ก่อนเปลี่ยน Mock ให้เป็นพฤติกรรมระบบจริง; การอนุมัติทำ Mock นี้ไม่ถือเป็นการอนุมัติกฎ OPEN หรือผ่าน Gate สำหรับงาน Production

### 22.5 รูปแบบพื้นที่เนื้อหาหน้ารายการ (2026-09-25)

- หน้ารายการทั่วไปไม่แสดงชื่อหน้า คำอธิบาย หรือปุ่มหลักซ้ำเป็น Page header แยก; วาง Tab bar ไว้ด้านบน และวางปุ่มหลักไว้ท้ายแถว Search/Filter ใต้ Tab
- หน้ารายการทั่วไปไม่แสดง KPI cards; Dashboard เป็นข้อยกเว้นที่แสดง KPI ได้
- เรียงเนื้อหาหน้ารายการเป็น Tab bar → Search/Filter และปุ่มหลัก → Data table/list → จำนวนรายการและ Pagination → Export ใต้รายการ ตามภาพอ้างอิงของเจ้าของโครงการ
- ตารางใช้เส้นคั่นบางและหัวตารางพื้นสีอ่อน รูปแบบกระชับ; รองรับการย่อจอด้วยรายการที่อ่านได้โดยไม่บีบคอลัมน์บนมือถือ
- ภาพอ้างอิงล่าสุดให้ Tab เป็นข้อความเรียบและเส้นใต้สีน้ำเงิน ไม่มีตัวเลขหรือป้ายในแถบ; Filter ใช้ label เหนือช่อง; ตาราง Desktop ใช้ 7 คอลัมน์แบบแถวเตี้ยหนึ่งบรรทัด; จำนวนรายการและหน้าอยู่ใน Footer ของตาราง และ Export ใต้ตารางซ้ายมือ

### 22.6 หน้าลูกค้า Mock ก่อนแตกเมนูย่อย (2026-09-25)

- เจ้าของโครงการขอให้ถอด Sidebar ย่อยของลูกค้าออกจากหน้าจอ Mock ก่อน หน้า `/customers` จึงแสดง Tab, Filter และรายการในพื้นที่เนื้อหาหลัง Sidebar หลักโดยตรง
- ยังไม่กำหนดโครงสร้างเมนูย่อยลูกค้าชุดใหม่; เส้นทาง Mock ย่อยที่มีอยู่เก็บไว้ชั่วคราวและไม่แสดงเป็นเมนูนำทาง จนกว่าเจ้าของโครงการจะระบุการแตกย่อย

### 22.7 ขนาดเนื้อหาหน้าลูกค้า Mock (2026-09-25)

- ใช้ขนาดและระยะห่างจากไฟล์ตัวอย่างที่เจ้าของโครงการส่ง: พื้นที่เนื้อหา Tab ใช้ padding 24px, Tab ใช้ขนาดตัวอักษร 14px และระยะล่าง 16px, กล่อง Filter ใช้ padding 24px และช่องกรองวางเรียงด้วยระยะ 20px
- ตารางเว้นจาก Filter 24px, หัวตาราง padding แนวตั้ง 12px/แนวนอน 14px, แถวข้อมูล padding แนวตั้ง 16px/แนวนอน 14px และ Pagination เว้นแนวตั้ง 20px

### 22.8 การจัดไฟล์ข้อมูล Mock รายหน้า (2026-09-25)

- แยกข้อมูลของแต่ละ route ไว้ในโฟลเดอร์เฉพาะ เช่น `src/features/mock/pages/customers/data.ts`; เก็บชื่อหน้า, tabs, filters, columns และ rows ของหน้านั้นในไฟล์เดียว
- โครง UI และ Mock renderer ใช้ร่วมกันได้ ไม่ต้องทำ page component หรือโครงหน้าซ้ำต่อ route

### 22.9 โครงหน้า App และขนาดเนื้อหาเทียบ TPSO (2026-09-25)

- เจ้าของโครงการให้ใช้โครงหน้า TPSO เป็นแนวทาง: แต่ละ URL ของ ZUU มีโฟลเดอร์และ `page.tsx` ของตนใน `src/app`; ข้อมูลตัวอย่างของหน้านั้นอยู่ร่วมใน `data.ts` เพื่อเปิดแก้รายหน้าได้โดยตรง. ปรับจาก §22.8 ซึ่งเคยให้ไฟล์ข้อมูลอยู่ใต้ `src/features/mock/pages` และใช้ catch-all route.
- ส่วนแสดงผลที่ใช้ซ้ำ เช่น Tab, Filter, ตาราง, Pagination และฟอร์มตัวอย่าง อยู่ใน component กลางได้; แต่หน้าแต่ละ URL ต้องมี entrypoint ที่แก้หรือแทนดีไซน์เฉพาะหน้าได้. ข้อมูลยังเป็น Mock สำหรับนำเสนอ.
- ใช้สัดส่วนตัวอักษรและระยะของ TPSO เป็นแนวทางกับพื้นที่เนื้อหา ZUU ทุกหน้าที่มีรายการ: Tab 14px; Filter label 12px, control/button 14px สูง 40px; กล่อง Filter padding 24px และ gap 20px; หัวตาราง 12px padding 12px × 14px; แถวตาราง 14px padding 16px × 14px; Pagination 14px และปุ่มสูง 36px; ตารางห่าง Filter 24px. หน้า Dashboard และฟอร์มใช้ขนาด/ระยะที่สอดคล้องกับเนื้อหาโดยไม่เพิ่มองค์ประกอบใหม่.
- คงสีทั้งหมด, Sidebar, Topbar, รูปแบบ responsive ที่มี, เมนู, ข้อความและฟังก์ชัน Mock เดิมไว้. ไม่เพิ่มการเชื่อมต่อ API/Auth/DB และไม่เปลี่ยนกฎธุรกิจ. §22.7 ยังคงเป็น baseline ของ `/customers`.

### 22.10 Padding กรอบเนื้อหาหลัก (2026-09-25)

- กรอบเนื้อหาหลักใต้ Topbar ที่ครอบหน้าและ Footer ใช้ Tailwind `p-6` (24px ทุกด้าน) ตามภาพที่เจ้าของโครงการชี้ แทนค่า `px-4.5 py-3.5 md:px-7.5 md:pb-4.5 md:pt-6` เดิม.
- ข้อนี้เปลี่ยนเฉพาะระยะของ wrapper ใน App Shell; สี, Sidebar, Topbar, padding ภายในหน้า, Footer และพฤติกรรมยังคงเดิม.

### 22.11 เส้นตารางแนวนอน (2026-09-25)

- ตารางรายการที่ใช้ร่วมกันและตารางผู้ใช้งานมีเส้นกรอบรอบนอกครบสี่ด้าน แต่ไม่แสดงเส้นคั่นคอลัมน์; คงเส้นคั่นแถวและเส้นเหนือ Pagination. ข้อนี้เป็นคำแก้ล่าสุดของเจ้าของโครงการหลังลองแบบไม่มีกรอบ.
- คงสี ระยะ ตัวอักษร ข้อมูล และการทำงานของตารางเดิม.

### 22.12 แสดงข้อมูลตารางเต็ม (2026-09-25)

- หัวคอลัมน์และข้อมูลในตารางรายการทุกหน้า รวมถึงตารางผู้ใช้งาน ห้ามตัดข้อความเป็น `...`; ให้ขึ้นหลายบรรทัดได้ภายในเซลล์ รวมถึงข้อความยาวที่ไม่มีช่องว่าง.
- การ์ดมือถือที่แสดงข้อมูลชุดเดียวกันต้องไม่ตัดชื่อหรือผู้รับผิดชอบเป็น `...`. คงข้อมูล สี กรอบตาราง และการทำงานเดิม.
- นำเข้าข้อมูลผ่าน registry กลางเพื่อรักษาการทำงานของ routing; แก้ไฟล์ข้อมูลหน้าหนึ่งแล้วข้อมูลหน้าอื่นต้องไม่เปลี่ยน

| Utilities / Folder | camelCase; ไฟล์ที่ Next.js บังคับใช้ `page.tsx`, `layout.tsx`, `route.ts` |

| Router | `useRouter` จาก `next/navigation` |

| HTTP | หน้าเว็บเรียกผ่าน `src/service/http.ts`; Axios อยู่ที่ชั้นนี้ |
| Logic ฝั่ง Server | แยกจาก HTTP Client และไม่ Import เข้า Browser; ใช้ Prisma เฉพาะ Server |
| Constants | `src/config/app.ts` เป็นจุดเข้ากลาง; แยกไฟล์ใน config ได้เมื่อใหญ่และ Export ผ่านจุดกลาง |
| Styling | HeroUI + Tailwind + CSS Variables ตาม Design ที่ผู้ใช้ให้ |
| Font | Poppins + Noto Sans Thai และ Weight Classes ตาม Guide/ทรัพยากรจริง |
| State Management | React Hooks + Context API |

| Import | React/Next → Libraries → Services → Components → Config/Types; ใช้ `@/` |
| Comment | Tag สั้นสำหรับแบ่งส่วน; JSDoc เฉพาะฟังก์ชัน/Component สำคัญ |
| Async/Error | จัดการ try-catch ตาม Guide รวม 401/403; ไม่กลืน Error หรือแสดง Stack/Secret บนหน้าเว็บ |
| Format | Prettier และกฎ Lint กลางของโครงการ |

### 23.1 ข้อที่แทนคำอธิบายใน Starter เดิม

- HeroUI แทน Shadcn ที่ปรากฏในบริบทโครงการก่อนหน้า
- Supabase Auth แทนการสร้างระบบ Password/JWT เอง
- API ธุรกิจอ่านเขียน PostgreSQL ผ่าน Prisma; `src/mocks` ใช้กับ Fixture/ตัวอย่างเท่านั้น
- Next.js API ไม่จำเป็นต้องเรียก Axios กลับเข้า API ตัวเอง ใช้บริการธุรกิจฝั่ง Server โดยตรง
- รุ่น Next.js/Prisma ที่เลือกอาจเปลี่ยนชื่อไฟล์ Config หรือวิธี Refresh Session ต้องระบุใน Plan ไม่คัดตัวอย่างเก่ามาใช้โดยไม่ตรวจ
- ตัวอย่างชื่อ Component บางไฟล์ใน Guide ใช้ตัวพิมพ์ไม่ตรงกฎหลัก งานใหม่ยึด PascalCase; ไม่ Rename งานคนอื่นเพื่อจัดรูปแบบโดยไม่มีขอบเขตงาน
- กฎเดิม “ทดสอบก่อนถือว่าเสร็จ” แยกเป็น AI ทำเสร็จ/ตรวจพื้นฐานแล้ว และผู้ใช้ตรวจการทำงานผ่านแล้วตามข้อ 27

## 25. Git และ AI หลายตัว

### 25.1 Branch และอำนาจทำงาน

| Branch | ผู้ใช้งานหลัก | ความหมาย |
|---|---|---|
| `AI` | AI ที่ได้รับ Task | งานพัฒนาและเอกสารของ AI สามารถ Commit/Push ภายในขอบเขตได้ |
| `Dev` | ผู้ใช้ | พื้นที่ที่ผู้ใช้แก้ ตรวจ และรวมงาน |
| `Main` | เวอร์ชันผ่านตรวจ | พร้อมใช้ตามขอบเขตรุ่นนั้น ไม่ใช่งานที่ยังรอทดสอบ |

- ใช้สาม Branch นี้ตามตัวพิมพ์ที่ตกลง ไม่สร้าง Branch ย่อย
- AI ไม่ต้องขออนุญาตซ้ำเพื่อ Commit/Push งานที่ได้รับมอบหมายเข้า `AI`
- การอนุญาตทำงานในพื้นที่โครงการไม่ได้เปลี่ยนการรับรอง Specs/Plan เป็นอนุมัติอัตโนมัติ
- การรวมเข้า `Dev`/`Main` ทำตามงานที่ผู้ใช้มอบหมาย ไม่ย้ายพื้นที่ผู้ใช้โดยพลการ
- Commit ภาษาไทยมีรหัส Task เช่น `เพิ่ม: [TASK-002] หน้ารายชื่อผู้ใช้งาน`
- ไม่ Commit Secret, `.env`, ข้อมูลจริง หรือไฟล์ส่วนตัว
- ไม่ Force Push หรือ Reset ทิ้งงานผู้อื่น

### 25.2 ป้องกันงานชนกัน

**ไฟล์ ACTIVE อย่างเดียวไม่ใช่ตัวล็อก:** หลายเครื่องอาจอ่านไฟล์รุ่นเดียวกันพร้อมกัน จึงต้องมีผู้ประสานงานหนึ่งรายจัดสรร Task/ไฟล์ก่อนเริ่ม และจัดคิวการแก้ไฟล์กลางกับการ Push

- Task มีผู้รับผิดชอบหลักคน/AI เดียว พร้อมรุ่น Specs/Plan และ Commit ตั้งต้น
- ระบุไฟล์/โฟลเดอร์ ตาราง และ API ที่จะเปลี่ยน รวมขอบเขตที่ห้ามแก้
- ผู้ประสานงานอัปเดตการถือครองขอบเขตจากข้อมูลล่าสุดและยืนยันให้ผู้รับงานก่อนเริ่มเขียน
- ถ้า Task ใหม่ต้องแก้ขอบเขตที่มีผู้ถืออยู่ ให้จัดคิวหรือแบ่งขอบเขตใหม่ ไม่เริ่มเขียนพร้อมกัน
- ไม่ให้หลาย Agent ใช้ Git index/checkout เดียวกันพร้อมกัน หากใช้เครื่อง/โฟลเดอร์เดียว ให้มีผู้ทำ Git operation ครั้งละหนึ่งราย
- ถ้าแยกโฟลเดอร์ทำงาน ให้ใช้ Clone แยกและ Branch `AI` ตามเดิม ไม่สร้าง Branch เพิ่ม
- ก่อน Commit ตรวจ diff และ Stage เฉพาะงานตน ไม่ใช้คำสั่งเก็บไฟล์ทั้งหมดโดยไม่ตรวจ
- ก่อน Push ตรวจ Remote ที่อัปเดต หากมี Commit ใหม่ต้องรวมอย่างระมัดระวังและตรวจขอบเขตไฟล์ซ้ำก่อน Push ปกติ
- การ Push ที่ถูกปฏิเสธเพราะ Remote เปลี่ยนไม่แก้ด้วย Force Push
- `schema.prisma`, Migration, Config, Layout, CSS กลาง, Permission และ Dependency/Lockfile มีผู้แก้ครั้งละหนึ่ง Task
- ฐานข้อมูลที่ใช้ร่วมกันมีผู้รัน Migration/Seed ที่กระทบข้อมูลครั้งละหนึ่งราย
- หากไม่มีช่องทางยืนยันผู้ถือ Task ล่าสุด ให้หยุดเฉพาะงานเขียนที่อาจชนและทำงานอ่าน/วิเคราะห์ที่ไม่กระทบต่อได้

### 25.3 สถานะงานและรายงาน

| สถานะ | ความหมาย |
|---|---|
| TODO | ยังไม่เริ่ม |
| IN_PROGRESS | มีผู้รับผิดชอบและกำลังทำ |
| BLOCKED | ทำต่อไม่ได้ ระบุสาเหตุและสิ่งที่ต้องใช้แก้ |
| READY_FOR_USER_TEST | ทำและตรวจพื้นฐานแล้ว รอผู้ใช้ทดสอบ |
| CHANGES_REQUESTED | ผู้ใช้พบปัญหา/ขอแก้ |
| DONE | ผู้ใช้ตรวจรับตามเกณฑ์แล้ว |

รายงานใช้เลขหัวข้อ Phase/Task ตาม Plan เช่น “Phase 5 / 5.1 ระบบพื้นฐาน” แล้วบอกทำอะไรแล้ว ไฟล์ใด ผลตรวจพื้นฐาน สิ่งที่ขาด เหตุผล และรายการให้ผู้ใช้ทดสอบ ไม่รายงาน Phase ว่าเสร็จทั้งชุดเมื่อยังมี Task ค้าง

ถ้ามีหน้าสถานะงาน ใช้สีเขียวเสร็จ สีฟ้ายังไม่เริ่ม สีแดงติดปัญหาพร้อมเหตุผล และมีข้อความสถานะกำกับ สีเหล่านี้ใช้กับการติดตามงาน ไม่แทนสถานะเอกสารทางธุรกิจ

## 26. สภาพแวดล้อมและ Docker

- ใช้ Docker ให้เครื่องใหม่เริ่มสภาพแวดล้อมที่ตรงกันได้
- ล็อกรุ่น Runtime, Package Manager และ Dependency ผ่านเอกสารกับ Lockfile ใน Plan
- ตำแหน่ง Supabase รุ่น Mock ว่าเป็น Project ทดสอบบน Cloud หรือชุด Local ต้องกำหนดก่อนเชื่อมต่อ ทั้งสองกรณีต้องเป็น PostgreSQL ที่ใส่ข้อมูลจำลองจริง
- ฐานข้อมูล Mock แยกจากข้อมูลจริง และต้องเห็นได้ว่าเครื่องนี้เชื่อม Environment ใด
- `.env` อยู่เฉพาะเครื่อง ส่วน `.env.example` อยู่ใน Git พร้อมชื่อค่าและวิธีรับค่า โดยไม่ใส่ Secret
- ค่าขั้นต่ำครอบคลุม App URL, DB runtime connection, DB migration connection ตามรุ่น Prisma, Supabase URL, Public Key, Server Key ที่จำเป็น และ Storage configuration
- ไม่ใช้ชื่อ `.env` ตายตัวจากตัวอย่างเก่าหากรุ่น SDK/Prisma เปลี่ยน ต้องบันทึกชื่อที่ใช้จริง
- Secrets ฝั่ง Server ไม่ขึ้นต้น `NEXT_PUBLIC_` และไม่อยู่ใน Bundle/Log/PDF
- การเชื่อม DB กับ Server โดยตรงในอนาคตยังต้องส่งค่าลับอย่างเหมาะสม ไม่ฝังใน Code
- README ต้องระบุ Clone → ตั้งค่า Environment → เริ่ม Docker → เตรียม DB → Migration → Seed → เปิดเว็บ → อ่านสถานะงาน
- Clone โค้ดไม่ได้ดึง Secret/DB/Storage ตามมาด้วย ต้องมีวิธีเตรียมสิ่งเหล่านี้เพื่อให้เริ่มงานได้ครบ
- คำสั่ง Seed/Reset และ Migration ต้องระบุผลกระทบชัด ไม่ใช้การล้างข้อมูลเป็นขั้นตอนเริ่มเว็บทุกครั้ง

## 27. การตรวจงานและรายการทดสอบ

### 27.1 หน้าที่ AI

- ตรวจเอกสารและขอบเขตงานให้ตรง Specs ที่อนุมัติ

นี่คือรายการตรวจระดับโครงการ ต้องเพิ่มขั้นตอนละเอียดและข้อมูลตัวอย่างจริงในแต่ละ Task เมื่อพัฒนาแล้ว ตารางนี้ยังไม่มีรายการใดถูกระบุว่าผ่าน

### 27.3 เกณฑ์ส่งงานและเกณฑ์ Done

- **พร้อมให้ผู้ใช้ทดสอบ:** ทำตาม Specs/Plan แล้ว ตรวจพื้นฐานที่เกี่ยวข้องแล้ว มีรายการทดสอบและเอกสารส่งต่อ พร้อมรายงาน Commit/Push
- **Done:** ผู้ใช้ตรวจผลตามเกณฑ์แล้ว ปัญหาที่ต้องแก้ปิดครบ หรือมีรายการยอมรับข้อจำกัดที่บันทึกชัดเจน
- หากตรวจไม่ครบคงสถานะ `READY_FOR_USER_TEST` หรือ `CHANGES_REQUESTED` ไม่ย้าย `Main` โดยอ้างว่าผ่านแล้ว
