# TASK-076 ชุดข้อมูลชื่อสมจริงใน DB

สถานะ: APPROVED — เจ้าของอนุมัติ “ทำได้เลย” 2026-10-02

## คำขอเจ้าของ

เพิ่มข้อมูลชื่อสมจริงครบทุกข้อมูล ลบชื่อซ้ำ/ชื่อรันเลข เช่น เอกสารลูกค้า 001–010 และเติมรายละเอียด ผู้ดูแล และฟิลด์ประกอบ เพื่อทดลองใช้ชุดข้อมูลที่ดูเหมือนงานจริง

## ขอบเขต

- ใช้ Supabase project ปัจจุบัน zuugroup-web ที่เจ้าของกำหนดเป็นสภาพแวดล้อมทดสอบแล้ว
- ผลตรวจอ่านอย่างเดียว: Records 14 โมดูลมีโมดูลละ 15 รายการ รวม 210 รายการ สินค้า 16 รายการ คลัง 18 รายการ มีชื่อรันเลขจาก seed จำนวนมาก ไม่เปลี่ยน Schema/API/UI
- ข้อมูลชื่อสมจริงแต่งขึ้น ไม่อ้างว่าเป็นรายชื่อลูกค้า ผู้ขาย หรือธุรกรรมจริงจากเจ้าของ ไม่เติมคำ mock/demo/ตัวอย่างในชื่อหรือ UI
- เปลี่ยนชื่อและเติมรายละเอียดของรายการตั้งต้นที่ยืนยันแหล่งที่มาได้ ไม่เพิ่มสำเนาชื่อซ้ำ เป้าหมายอย่างน้อย 15 รายการใช้งานต่อโมดูลสำหรับลอง pagination
- Snapshot พบลูกค้าที่เจ้าของลบเชิงตรรกะหนึ่งรายการ คง deletedAt/deletedBy/deleteReason ทั้งหมด แก้เฉพาะชื่อ/ข้อมูลตั้งต้นที่ยังตรง seed โดยตรวจ timestamp/สถานะลบก่อนเขียน ไม่กู้คืนรายการ; ลูกค้าจึงคง 14 ใช้งาน + 1 ลบแล้ว รายการรวมเดิม 15
- รักษา ID/code/product sequence เดิม และความสัมพันธ์เดิม เว้นแต่ relation ว่างของรายการตั้งต้น ให้เชื่อมกับลูกค้า/ผู้ขาย/คลังที่เหมาะสมและบันทึกผล
- ผลตรวจสินค้าเดิม: seed ผูก Normal saline และ Oral rehydration salts กับรหัส MED-TAB ซึ่งไม่ตรงรูปแบบยา จัดข้อมูลสองรายการนี้ใหม่เป็นยาชนิดเม็ด โดยแก้ drugId เฉพาะรายการที่ชื่อ/ตัวยา/หน่วย/ราคาเดิมตรง seed ทั้งชุด คง ID/code/sequence/category/form และบันทึก before/after; สินค้าชื่อ test ที่เจ้าของเพิ่มคงเดิม
- ตรวจรายการจาก seed code และค่าเดิมร่วมกัน ไม่ใช้แค่ code prefix ตัดสินเขียนทับทั้งแถว หากผู้ใช้แก้ฟิลด์ไว้แล้ว คงค่านั้นและรายงานรายการข้าม
- ตรวจข้อมูลที่ import จาก fixtures/operational-migration-backup.json และ record_import_map ด้วยค่าเดิมก่อนปรับ ไม่แก้ข้อมูลผู้ใช้เองที่ไม่มีหลักฐาน seed
- subtitle เป็นรูปแบบแสดงผลจากฟิลด์จริง เช่น category/description/documentType/province ไม่สร้างคอลัมน์หรือ API alias subtitle ใหม่ ใช้ owner/contact/notes ที่มีจริงตามโมดูล

## ข้อจำกัดข้อมูลและวิธีลง

- เก็บสถานะเดิม หากชุดข้อมูลมีสถานะเดิมหลายค่าให้คงความหลากหลายนั้น ไม่สร้าง workflow หรืออนุมัติเอกสารเอง
- ราคาและ amount เป็นข้อมูลหัวเอกสารสำหรับลองหน้าเท่านั้น ไม่คำนวณภาษี/ส่วนลด/กำไร/ลูกหนี้ ไม่สร้างรับชำระ/ยอดคลัง/Ledger
- ไม่แก้ผู้ใช้ Role Auth รหัสผ่านหรือ Audit เก่า เพิ่ม Audit สรุปงานลงข้อมูลหนึ่งเหตุการณ์ตามการทำงานจริง
- เก็บ snapshot เฉพาะข้อมูลธุรกิจที่เปลี่ยนพร้อม before/after เพื่อย้อนกลับรายการชุดนี้ได้ ไม่สำรอง secrets/Auth
- เขียน transaction เดียว ใช้ parameter binding/identifier allowlist ตรวจค่าเดิมก่อน UPDATE รันซ้ำแล้วไม่สร้างข้อมูลซ้ำหรือทับค่าที่ผู้ใช้แก้
- เปลี่ยน seed เดิมให้สร้างชุดชื่อสมจริงเมื่อติดตั้งใหม่ ไม่ให้ seed ครั้งต่อไปสร้างชื่อรันเลขกลับมา

## ตรวจรับ

ชื่อสินค้า/ลูกค้า/เอกสาร/คลังไม่เป็นชื่อรันเลข รายละเอียดและผู้ดูแลมีความหมาย ฟิลเตอร์มีค่าหลากหลาย เปลี่ยนหน้าได้ รายละเอียดและความสัมพันธ์ตรงกับชื่อ API key คงเดิม; จำนวนรายการไม่หาย ข้อมูลที่ผู้ใช้แก้และบัญชีเดิมไม่เปลี่ยน
