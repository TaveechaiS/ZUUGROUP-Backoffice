# TASK-063 — SuccessAlert ทุกการเปลี่ยนข้อมูล

สถานะ: เจ้าของอนุมัติ 2026-10-02. เจ้าของแจ้งใช้งานได้ OK แต่ยังไม่ได้ตรวจ SuccessAlert ทุก flow.

ข้อกำหนดเพิ่มจากภาพ: ไม่ใช้กล่อง native ของ browser ที่ขึ้น localhost says. ใช้ ConfirmationDialog ของเว็บสำหรับยืนยันลบรายการ/ผู้ใช้/สินค้า สไตล์เดียวกับ dialog เดิม สีจาก tokens และปุ่มไทย ยกเลิก/ยืนยันลบ. ยกเลิก/X/Escape/พื้นหลังต้องไม่ส่งคำขอ; ขณะยืนยันแล้วรอ server ห้ามยืนยันซ้ำและไม่ปิดกลางคำขอ. บันทึกสำเร็จปิด confirmation ก่อนเปิด SuccessAlert; ล้มเหลวปิด confirmation แล้วแสดง error เดิม ไม่มี success. ไม่เพิ่ม confirmation ให้ทุกการบันทึกโดยไม่จำเป็น.

## ขอบเขตและผลสำรวจ

คำท้วงต่อ 2026-10-02: เติม custom confirmation ก่อนบันทึกการแก้ไขข้อมูลรายโมดูล/สินค้า/ข้อมูลบัญชีผู้ใช้ (เดิมส่งทันที). ใช้ปุ่มสีน้ำเงิน “ยืนยันบันทึก”, ข้อความ “กำลังบันทึก...” และ snapshot ค่าที่กดบันทึก. ยกเลิกแล้วคงค่าในฟอร์มและไม่ส่ง PATCH; สำเร็จมี SuccessAlert หลัง server ยืนยัน. การสร้างและปุ่มจัดการอื่นคง flow ที่ทำไว้.

| กลุ่ม | การเปลี่ยนข้อมูล | โค้ดปัจจุบัน |
|---|---|---|
| 14 โมดูลข้อมูลหลัก/หัวเอกสาร | สร้าง แก้ ลบเชิงตรรกะ กู้คืน | RecordFormPage, RecordDetailPage, ModuleListPage มี alert แล้ว |
| สินค้า | สร้าง แก้ข้อมูล เปลี่ยนสถานะ ลบ กู้คืน | create-product-form และ product-detail มี alert; เปลี่ยนสถานะผ่านบันทึกฟอร์ม |
| ข้อมูลแม่สินค้า | เพิ่มหมวดหมู่ยา รูปแบบยา ตัวยา | addMaster มี alert ร่วม แต่ไม่มี pending state เฉพาะ จึงต้องป้องกันกดซ้ำ |
| ผู้ใช้ | สร้าง แก้ข้อมูล/รหัสพนักงาน เปลี่ยนบทบาท ระงับ เปิดใช้งาน ตั้งรหัสผ่านใหม่ ลบ กู้คืน | create-user-form/user-detail มี alert; แยกคำระงับ/เปิดใช้งานจากข้อความทั่วไป |

ไม่สร้างปุ่มธุรกิจใหม่จากแผนนี้. การค้นหา/filter/pagination/เปิดหน้า/เลือกค่า/ยกเลิกไม่บันทึกข้อมูลจึงไม่มี success dialog. Login/logout ใช้การนำทางปัจจุบัน; ไม่เพิ่ม dialog ขวางการเข้า/ออกระบบ. การอนุมัติ รับชำระ รับเข้า/โอน/ตัดสินค้า ส่งออก และแนบไฟล์จริงยังไม่อยู่ในขอบเขตนี้ เมื่อเปิด flow ใหม่จึงใช้มาตรฐานเดียวกัน.

## มาตรฐานพฤติกรรม

1. เปิด SuccessAlert หลัง server ยืนยันการบันทึกสำเร็จและ response ตรง contract เท่านั้น; อย่าแสดงหลังเพียงกดปุ่มหรือจบ loading.
2. ระหว่างคำขอค้าง ปุ่มของ operation เดิม disabled มีข้อความกำลังทำงานและ guard การ submit ซ้ำ; เมื่อ alert เปิดป้องกัน mutation ซ้ำจนปิด. ไม่ retry POST โดยอัตโนมัติเมื่อ network ขาด.
3. ข้อความภาษาไทยเจาะจง action เช่น เพิ่มลูกค้าแล้ว, แก้ไขสินค้าแล้ว, ลบผู้ใช้งานแล้ว, กู้คืนรายการแล้ว, ระงับการใช้งานแล้ว, เปิดใช้งานแล้ว, เปลี่ยนบทบาทแล้ว, ตั้งรหัสผ่านใหม่แล้ว; ไม่แสดงรหัสผ่าน/token ใน alert.
4. ถ้าต้องเปลี่ยน URL หลังสร้าง/ลบ/แก้รหัสพนักงาน รอปิด alert ก่อน; ถ้าอยู่หน้าเดิมอัปเดตข้อมูลและ alert แสดงหนึ่งครั้ง. ปิดด้วยตกลง/X/Escape/พื้นหลังมีผลหลังปิดเหมือนกัน; default ไม่ auto close.
5. Error, validation, 401/403/409/503, cancel confirmation หรือ network ขาด ห้ามแสดง SuccessAlert; แสดง error ที่อ่านได้และให้ลองใหม่อย่างระมัดระวัง. หากคำขออาจบันทึกไปแล้วแต่ response หาย ให้ตรวจรายการก่อนทำซ้ำ.
6. ใช้ component เดิม มี focus ภายใน, Tab/Shift+Tab, Escape และ reduced motion. ไม่มี alert ซ้อนหรือแจ้งสำเร็จจาก GET reload.
7. Scope UI/client เท่านั้น; ไม่แก้ schema/seed/endpoint/RBAC หรือข้อจำกัด Admin คนสุดท้าย.

## ตรวจรับ

ทุก mutation ที่มี UI ต้องมีช่องในตารางตรวจรับ ระบุหน้าปุ่ม/action/ข้อความ/เวลานำทาง/ผลจริง. Shared CRUD ต้อง smoke ทุกรายโมดูลเพื่อยืนยัน metadata/route ไม่เพียงทดสอบหนึ่งหน้า. ทดสอบผู้ใช้บนบัญชีทดลองที่ไม่ใช่ตัวเอง/Admin คนสุดท้าย. คู่มือไม่ใส่รหัสผ่านจริง. เจ้าของเป็นผู้ตรวจ UAT; ไม่ยิง HTTP/ล็อกอินอัตโนมัติโดยไม่ได้รับคำสั่งใหม่.
